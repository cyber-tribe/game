# 少年ガルドと迷いの洞窟

[![CI](https://github.com/cyber-tribe/game/actions/workflows/ci.yml/badge.svg)](https://github.com/cyber-tribe/game/actions/workflows/ci.yml)

ブラウザで動く 3D のローグライク。潜るたびに地形が変わる洞窟を、
ターン制で一歩ずつ進んでいく。

TypeScript + Three.js。**3Dモデルはすべてこのリポジトリの中で Blender から作っている**
(`tools/models/`)。外部から持ってきた素材は一つも使っていない。

> ターン制で潜るローグライクを一から作りたい、という要望から始まったもの。
> 遊びの骨組みはこのジャンルの定石を踏まえているが、世界観・名前・造形・設定は
> すべてこのリポジトリのオリジナルで、既存タイトルから持ち込んだものは無い。

## 遊びかた

**[ブラウザで今すぐ試遊する](https://cyber-tribe.github.io/game/)**
(mainブランチの最新ビルドを常時公開している。セーブデータはブラウザの
`localStorage` にだけ残り、他の人と混ざったり共有されたりしない)

ローカルで動かす場合:

```bash
npm install
npm run dev      # http://127.0.0.1:5173/
```

`npm run build` で `dist/` に静的ファイルとして書き出せる。Blender は遊ぶだけなら要らない。

### 操作

| キー | できること |
|---|---|
| 矢印 / WASD / テンキー | 8方向に移動。モンスターがいる方向へ進むと1マス押し出す |
| **X** | **向いている方向へ攻撃する(その場から動かない)。何もいなければ空振り(ターンは消費する)** |
| Shift + 方向 | その場で向きだけ変える(ターンを消費しない) |
| Space | 足元のものを拾う。階段の上なら次の階へ降りる |
| `.` / テンキー5 | 足踏み(1ターンやり過ごす) |
| **F** | **正面か足元のタルを持ち上げる。抱えていれば下ろす** |
| **G** | **抱えているタルを向いている方向へ投げる** |
| I | もちものを開く |
| T | 仲間への指示(構え)を開く |
| C | 樽守りの技を繰り出す |
| Q / E | 視点を90度回す |
| `+` / `-` | ズーム |
| R | めざめの階段(チェックポイント)の上で、そこまでを区切って持ち帰る。倒れたあとは拠点に戻る |
| P | フォトモードの切り替え(HUDを隠し、視点操作だけで画角を作れる) |
| H | 操作説明の表示切り替え |

### 流れ

洞窟のふもと(拠点)で、倉庫から持ち込む道具を **8個まで** 選んで潜る。
地下48階(8つの地方 × 6階)まで降りれば踏破。**倒れると持ち込んだ道具はすべて失う。**
踏破して戻れたぶんだけが倉庫に残るので、「良い杖を使いたいが失うのは惜しい」
という悩みがここで生まれる。

表の寝穴では、地方の最終階(6階ごと)の階段だけが**めざめの階段**になる。
足を踏み入れた瞬間に「既知」として記録され、以後消えない。**R** キーで
そこまでの成果を区切って持ち帰るか、そのまま先へ進んで深追いするかを
選べる。次のダイブでは、拠点の出発地点選びで既知のめざめの階段から
直接始められる。

満腹度はターン経過で減っていく。0 になると HP が減り続けるので、
食料を確保しながら階段を目指すことになる。

3階以降、まれに**モンスターハウス**(近道屋の乱掘で夢のかけらが渋滞して
溜まった部屋)に出くわす。部屋の外まで来ると気配の一言で予告されるので、
踏み込むかどうかは自分で判断できる。踏み込めば一部屋にひしめく数体が
一斉に襲いかかってくる代わりに、部屋の中には豪華な収穫物が置かれている。

### タルと仲間

洞窟にはタルが転がっている。**投げる武器であり、同時にモンスターを捕まえる容器**でもある。

| タル | 投げるとどうなるか |
|---|---|
| からのタル | 当たった相手にダメージ。**確率でモンスターを吸い込む** |
| ばくはつタル | 着弾点とその周囲もろとも吹き飛ばす。**自分も巻き込まれる**(ダメージは半分) |
| モンスター入り | 中身が飛び出して**仲間になる** |

吸い込める確率は相手の残りHPで決まる。満タンならまず入らず(12%)、瀕死ならほぼ確実(85%)。
だから手順は自然と「殴って弱らせてから、タルをぶつける」になる。

仲間は連れて歩ける(2体まで)。敵を見つければ勝手に向かっていって戦い、いなければ
ついてくる。階段にもついて来る。仲間の上を歩くと位置が入れ替わるので、通せんぼで
足止めされることはない。**ただし爆発には巻き込まれる。**

**T** キーで仲間に「構え」を指示できる。おまかせ(既定)・そばにいろ・そこで待て・
先陣を切れの4種類があり、全員まとめて、または1体ずつ指示できる。捕まえた直後は
常に「おまかせ」から始まる。

タルは置いたマスを塞ぐので、通路に置いて道を封じる使い方もできる。
抱えているあいだはアイテムを拾えない。

## 中身の作り

このプロジェクトの設計上いちばん大事なのは、**ゲームのロジックと描画を完全に分けてある**こと。

```
プレイヤー入力 → core が1ターン分を即座に解決 → GameEvent[] を返す
                                                   ↓
                       view がイベントを再生(移動の補間・攻撃モーション・被弾表示)
                                                   ↓
                                   再生が終わったら次の入力を受け付ける
```

`src/core` `src/dungeon` `src/entities` `src/items` `src/systems` は Three.js にも DOM にも
一切依存していない。だから Node 上でそのままテストできるし、見た目を差し替えても
ゲームの中身には触らずに済む。1ターン分のイベントは順番にではなく **同時に** 再生する。
順番に流すとモンスターが増えるほど1ターンが長引いて、遊べたものではなくなるため。

```
src/
  core/        乱数・座標・型・イベント定義   ← 描画非依存
  dungeon/     フロア生成・視界・配置          ← 描画非依存
  entities/    プレイヤー・モンスター・AI      ← 描画非依存
  items/       アイテム定義・持ち物・効果      ← 描画非依存
  systems/     戦闘計算                        ← 描画非依存
  game.ts      状態の集約とコマンド受付        ← 描画非依存
  view/        Three.js の描画・カメラ・入力・HUD・ミニマップ
  ui/          もちものメニュー・拠点
  save.ts      localStorage への保存
```

### フロア生成

マップを 2×3〜3×3 の区画に切り、各区画に部屋を置いて、区画どうしを全域木で結んでから
通路を掘る。回り道を作るために辺を数本だけ足す。

生成のあと **フラッドフィルで全部の床タイルに階段から到達できることを検証**し、
満たさなければ作り直す。「進めなくなるフロア」は原理的に出てこない。
テストでは 1000 シードぶんこれを確かめている。

### 追跡AIと陣営

毎ターン、マップ全体に歩数を広げた距離場(ダイクストラマップ)を作り、その階の全員で
使い回す。各自は値が小さくなる方向へ進むだけで、壁を回り込んで相手に近づく。

仲間が加わったので、この距離場は**始点を複数受け取れる**ようにしてある。

- モンスターには「プレイヤーと仲間すべて」を始点にした距離場を渡す
- 仲間には「敵すべて」を始点にした距離場を渡す

始点をまとめて入れておけば、各自が自然といちばん近い相手へ向かう。攻撃も追跡も
「相手が別の陣営か」だけを見ているので、陣営が増えても分岐は増えない。

### 速さのために効いていること

計測すると、重いのは思っていた場所ではなかった。実測して分かったことを残しておく。

**1ターンの計算は 0.17〜0.31ms**(地下1〜40階、アクター5〜34体)。ここは
ボトルネックではない。距離場は毎ターン作り直しているが、BFS の内側で
座標オブジェクトを作らないようにしてあるのと(そこだけで毎ターン万単位の
使い捨てが出ていた)、プレイヤーへ向かう距離場は仲間がいるときだけ作るのとで、
素朴に書いた場合の半分以下に収まっている。

**ダイブ中のオートセーブは、タイル格子を畳んでから書く。** 1ターンごとに
`localStorage` へ同期で書き出すので、ここが膨らむと操作が引っかかる。
タイルをそのまま JSON にすると1マス55バイト × 1728マスで94KB(スナップショット
全体の94%)になるため、地形は1マス1文字の文字列、探索済み・可視はビット列に
畳んでいる。`roomId` は部屋の矩形から引き直せるので保存しない。
結果、100KB前後 → 6〜14KB。記録まわりの更新も、1ターンぶんをまとめて1回だけ書く。

**描画は「変わったときだけ」やる。** ターン制で、ターンとターンの間は絵が
止まっているので:

- 影は毎フレーム作り直さない(`shadowMap.autoUpdate = false`)。ターンが解決した
  ときとアニメーション再生中だけ更新する。影を落とす光は1灯で、視錐台は
  カメラの注視点に追従させている(盤面は48×36マスあるので、原点に固定したままだと
  原点付近にしか影が出ない)
- 拠点画面が前に出ているあいだは、裏の洞窟を毎フレーム描かない。うっすら見える
  演出は残したいので止めはせず、更新の間隔を落としている
- 壁と床の `InstancedMesh` は、視界が変わったマスだけ書き直す。全部書き直して
  行列(1728×16 float ≒ 110KB)ごと送り直すのは、1マス歩いただけでは割に合わない

**表示物は使い終わったら捨てる。** スキンメッシュはインスタンスごとに
スケルトンを持ち、three はそこにボーン行列用のテクスチャを1枚確保する。
これはモデル間で共有されないので、`ActorView.dispose()` で捨てないと階を
降りるたびに積み上がる(直す前は1階あたり約2.4枚ずつ増え続けていた)。
逆にジオメトリと素のマテリアルは `SkeletonUtils.clone` が共有しているので、
捨ててはいけない。被弾で光らせるときだけ、そのインスタンス専用の
マテリアルを複製する(共有物に書き込むと、同じ種族が全員光ってしまう)。

**モデルは2段階で読む。** 起動時に全部(22個・約1.4MB)を待っていると、
モンスターの種類が増えるたびに起動が延びる。種族は増え続ける前提なので、
ここは放っておくと悪化し続ける唯一の場所だった。

いま待つのは `essentialModelNames()`(`src/modelList.ts`)が返すぶん
——主人公・地形・タルと、地下1階に出る種族——だけで、残りは
`Assets.loadInBackground()` で背景から追いかける。

まだ届いていないモデルを使う場面は「待つ」のではなく**その回を飛ばして、
届いた次のターンに拾う**。`syncActors` も `DungeonView.refresh` も
ギャラリーの `show` も毎ターン(毎フレーム)呼ばれるので、それだけで
自己修復する。フロアの組み立ては `submit()` の同期経路にも入っていて、
そこに `await` を差し込むと入力処理まで非同期化が波及してしまうため。

Fast 3G 相当で測ると、操作可能になるまで **8.2秒 → 4.6秒**、
そこまでに取りに行く `.glb` が **22個 1,377KB → 9個 665KB** になる。

**配信するJSは three とゲームコードで分けてある。** `main` へのマージの
たびに Pages へ自動公開しているので、1つにまとめたままだとゲーム側を
1行直すだけで three ごと再ダウンロードさせることになる。分けた結果、
毎回の再取得は 223KB → 69KB(gzip)。合計サイズは CI で見張っている。

**この節の数字はテストで固定してある**(`tests/perf-budget.test.ts`)。
1ターンに作る距離場の本数とオートセーブの書き出し量は機械の速さに
左右されないので、そこを主役にして見張っている。

## 3Dモデル

`tools/models/` の Python スクリプトが Blender を動かしてモデルを作り、
`public/models/*.glb` に書き出す。GUI が無いだけで、やっていることは通常のモデリングと同じ。

キャラクターは **関節の位置と太さを定義して Skin モディファイアで皮を張り、
サブディビジョンで丸める**。Blender で生物のベースメッシュを作るときの定石で、
結果は継ぎ目のない一枚のメッシュになる。そこにアーマチュアを自動ウェイトで結びつけ、
ポーズをキーフレーム化して 5 つのクリップ(待機・歩行・攻撃・被弾・消滅)を焼き込む。

```
関節と太さ → Skin + サブディビジョン → 一枚のメッシュ
                                            ↓
                           アーマチュア + 自動ウェイト → 動かせるキャラ
                                            ↓
                                   キーフレーム → 5クリップ
                                            ↓
                                         .glb
```

造形は Cycles でレンダリングして目で確認しながら詰めた。その画像は `tools/preview/` にある。

| | 名前 | 三角形 |
|---|---|---|
| 主人公 | ガルド | 5,864 |
| | ぷるん | 1,780 |
| | あくびとかげ | 1,908 |
| | ガジリねずみ | 6,036 |
| | ツブテガエル | 4,100 |
| | マドロミダケ | 1,960 |
| | ホネガラミ | 7,496 |

壁・床・階段・罠4種・アイテム6種・タル3種も同じ仕組みで作ってある。壁と床は数が多いので
`InstancedMesh` にまとめ、さらに **歩けるマスに面している壁だけ** を描いている。

タルは面数を12に落としたうえでフラットシェーディングにしてある。側面の平らな面が
そのまま板張りに見えるので、板を1枚ずつ並べなくても樽らしくなる。

### モデルを作り直す

```bash
bash tools/setup_blender.sh   # bpy を入れる(約1GB。最初の一度だけ)
npm run models                # 全部作り直す
tools/venv/bin/python tools/build_models.py garudo --no-preview   # 1体だけ、プレビューなし
```

`bpy` 5.0 は CPython 3.11 専用。スクリプトと生成された `.glb` の両方をコミットしてあるので、
形を直したいときはスクリプトを書き換えて作り直せばよく、遊ぶだけの人は Blender を入れずに済む。

> **`npm run models` のあと、形を変えていなくても `.glb` に差分が出る。**
>
> Blender の出力は、同じマシンで同じスクリプトを2回走らせても一致しない。揺れは2種類ある。
>
> - **バイトの揺れ** — `uv_sphere` を含むモデルで毎回わずかに変わる(ファイルサイズは同じ)。
>   `PYTHONHASHSEED` を固定しても残る。
> - **位相の揺れ** — Skin モディファイアの出力する頂点数そのものが変わる。ツブテガエルを
>   単体で4回作り直したら 20678 / 21434 / 22490 と3通りに割れた。胴が太く四肢が広い角度で
>   生えているため、皮の張り方の解決が数値的に際どいらしい。
>
> どちらも形が変わったわけではないので、意図した変更が無ければコミットせず
> `git checkout -- public/models` で戻してよい。CI の `tools/compare_models.mjs` は
> メッシュ数・ノード数・クリップ名といった構造と、**外形(バウンディングボックス)** を
> 比べている。外形は上記の揺れの下でも小数点以下4桁まで一致するので、
> 寸法を変えて作り直し忘れた場合だけが落ちる。

## テスト

```bash
npm run test        # ユニットテスト (952件)
npm run typecheck
```

ダンジョン生成は 1000 シードで到達可能性を検証している。ほかに戦闘計算、ターン進行、
満腹度、持ち物、状態異常、レベルアップ。

`.glb` はビルド済みのものをコミットしているので、作り直しを忘れたり壊れたものを混ぜたりしても
気づけない。そこで `tests/models.test.ts` が glTF の中身を直接読み、モデルが全部そろっているか、
キャラクターに 5 つのクリップとスキンがあるか、ファイルが肥大していないかを検査している。
必要なモデルの一覧は `src/modelList.ts` に一本化してあるので、モンスターを足して
`.glb` を作り忘れれば、そのままテストが落ちる。

実機の動作確認はヘッドレスブラウザで行う。

```bash
npm run dev &
npm run playtest      # スクリーンショットは ./playtest-shots に出る
```

拠点から潜り、歩いて戦ってアイテムを使い、倒れて拠点に戻るまでを実際に操作して、
ページ内で例外や 4xx が出ないことを確認する。GPU の無い環境向けに WebGL は
SwiftShader で動かしている。

SwiftShader は1フレームぶんのラスタライズを丸ごと CPU でやるので、所要時間はほぼ
画素数に比例する。そのためビューポートは 800×500 に絞り、スクリーンショットも
各場面1枚(計10枚)にしてある。

**操作のあとは固定時間で待たず、再生が終わったかを見て待つ**(`__app.debugIdle()`)。
App は再生中に届いた入力を捨てるので、固定待ちだと遅い環境で入力が握り潰され、
「押したのに1ターンも進んでいない」が静かに起きる。実際これのせいで、以前は
足踏み40回のうち10回前後しか実際のターンになっておらず、命名ダイアログが
開きっぱなしで以降のキーが全部飲み込まれていたのに気づけなかった。

### CI

`.github/workflows/ci.yml` が PR と `main` への push で走る。

| ジョブ | いつ | やること |
|---|---|---|
| 型・テスト・ビルド | PR と `main` への push | `npm ci` → 型チェック → テスト952件 → 本番ビルド。`dist/` を成果物として残す |
| 実機での通しプレイ | PR と手動実行 | ビルドしたものをプレビューサーバーで配り、Chromium で上記の通しプレイを実行。スクリーンショットを成果物として残す |

この2つは**並列に走る**。通しプレイは CI の中でいちばん長いので、型チェックの
完了を待たせるとそのぶん丸ごと後ろにずれる。型エラーで落ちる PR では通しプレイが
無駄になるが、待ち時間の短縮を優先している。

通しプレイは数分かかるため `main` への push では走らせない。マージ後は軽いほうだけを
流して、「個々は緑だった変更が合流して壊れた」を捕まえる。

Chromium は `~/.cache/ms-playwright` をキャッシュしている。毎回ダウンロードすると
30秒前後かかり、ビルドやテストより長くつく。`PLAYWRIGHT_VERSION` を上げたときだけ
取り直す。

モデル制作の側は別枠にしてある(`.github/workflows/models.yml`)。Blender は約 374MB の
ダウンロードを伴うので毎回は回さず、`tools/models/**` や `public/models/**` に手が入ったときと
手動実行のときだけ、スクリプトから全モデルを作り直せるかを確かめる。

#### ドキュメント・モデルだけの変更はスキップされる

`design/` `plan/` `*.md` `tools/models/**` `public/models/**` など、実行コードに触れない
変更だけの PR では、上の2ジョブは **動かずに「スキップ」として緑になる**。

このプロジェクトはゲームプランナー役のセッションが仕様書を1件ずつ PR にして次々マージする
運用をしており(`CLAUDE.md` 参照)、その大半は `design/` `plan/` 配下の md だけの変更になる。
そのたびに数分かかる本番ビルドや実機プレイまで待たされるのは見合わない。

ここで単純に `on.pull_request.paths` でトリガー自体を絞る方法は取っていない。
それをやると、対象外のコミットに対してワークフローが一度も起動せず、必須ステータス
チェックが「pending」のまま残ってマージできなくなる(ブランチ保護で必須チェックに
指定した場合の既知の落とし穴)。

代わりに `changes` という判定ジョブを先頭に置き、`dorny/paths-filter` で
「実行コードに関わるファイルが変更されているか」を毎回判定する。ワークフロー自体は
必ず起動するが、コードに変更が無ければ後続の2ジョブは job 側の `if` で丸ごとスキップする。
**GitHub はジョブが `if` でスキップされた場合、そのジョブのステータスチェックを
「成功」として扱う**ため、必須チェックに指定していても待たされずマージできる。

push (main へのマージ後) と手動実行は、この判定を通さず常にフルで実行する。
「その push が何を含むか」の基準を取り違えると気づかず検査を素通りしてしまうため、
頻度の低い経路まで凝った判定をする価値は無いと判断した。同様に、判定ジョブ自体が
失敗した場合も「フル実行する」側に倒してある(判定が壊れて静かに検査を素通りする方が怖い)。

### 依存関係の自動更新

`.github/dependabot.yml` が npm 依存(`package.json`)と GitHub Actions
(`ci.yml` / `models.yml` の `uses:`)を週1回チェックし、それぞれまとめて1本のPRにする。

patch/minor の更新は `.github/workflows/dependabot-auto-merge.yml` が
`dependabot/fetch-metadata` で更新種別を見て auto-merge キューに載せる。実際に
マージされるのは通常のPRと同じく `ci.yml` の必須チェックが通った後(`package.json` /
`package-lock.json` の変更は `changes` ジョブで「コード」判定されるので、型チェック・
テスト・ビルド・通しプレイがそのまま走る)。major 更新は auto-merge をかけず、PRを
開いたままにして人がレビューする。

Blender モデル生成にだけ使う `bpy` (Python) はバージョンを固定していない
(`tools/setup_blender.sh` / `.github/workflows/models.yml` とも `pip install bpy` で
毎回最新を取得)ため、Dependabot の対象には含めていない。

## モバイル配信

複数プラットフォーム展開と収益化を目的に、[Capacitor](https://capacitorjs.com/) で
Web 版のビルド(`dist/`)をそのままネイティブの WebView に包んでアプリ化する方針にしている。
経緯は [`adr/0001-mobile-release-via-capacitor.md`](adr/0001-mobile-release-via-capacitor.md) を参照。
ゲームロジック・描画コードは変更せず、配信形態が増えるだけという位置づけ。

```bash
npm run build         # dist/ を作る
npx cap add android   # 初回のみ。android/ ネイティブプロジェクトを生成
npx cap add ios       # 初回のみ。ios/ ネイティブプロジェクトを生成(macOS + Xcode が要る)
npm run cap:sync      # dist/ をビルドし直してネイティブ側に反映
```

`cap add` はローカルの Android Studio / Xcode を前提にしており、この環境(CI含む)には
ネイティブツールチェインが無いため、`android/` `ios/` の生成はまだ行っていない。
そのため、この時点ではタッチ操作向けのUI/UX(仮想パッド等)も未着手。
