# 0014: サーバーを持たず、GitHub Actions をプレイヤー起点のバックエンドとして使う

- ステータス: 決定
- 日付: 2026-08-13

## 背景(Context)

このゲームはこれまで `localStorage` だけで完結するクライアント単体の
構成で作ってきた(`design/yorishiro-moods.md` 等、多くの文書がこの
前提で書かれている)。ただしそれは「サーバーを持たない設計にする」
という決定ではなく、単に今のところサーバーが無いという現状の観測に
過ぎなかった。バグ報告(`src/entities/debugPanel.ts`)のように、実際に
サーバー側の処理が要る機能が出てきたことで、方針を明文化する必要が
生じた。

READMEにある「外部から持ってきた素材は一つも使っていない」「すべて
自作」という姿勢とも関わり、外部SaaSにプレイヤーデータを預けない
構成を志向している。一方でブラウザで動くクライアントである以上、
コードは誰でも読める。ここに書き込み権限を持つ秘密情報を埋め込めば、
抜き出されて悪用されるリスクを常に抱えることになる。

## 検討した選択肢

| 案 | 概要 | 評価 |
|---|---|---|
| **専用バックエンドを新設する(自前サーバー・BaaS等)** | Firebase等のBaaSや自前のAPIサーバーを用意し、通常のクライアント→サーバーAPI構成にする | ホスティング費用・運用の手間が新たに発生する。外部SaaSにデータを預けることになり、自作方針とも相性が悪い |
| **クライアントに書き込みトークンを埋め込み、直接GitHub API等を呼ぶ** | ブラウザから直接GitHubへ書き込む | ブラウザで動く以上コードは誰でも読めるため、埋め込んだトークンが抜き出されて他人に悪用される(リポジトリへのスパム投稿等)リスクを常に抱える。この方式は原則から除外する |
| **GitHub Actions をサーバーの実行基盤にし、書き込み操作はプレイヤー自身のGitHub操作を起点にする** | クライアントは`github.com`上の操作(Issue作成画面のプレフィル等)の入口を開くだけに留め、実際の書き込みはプレイヤー自身のブラウザ・GitHubアカウントで行う。サーバー側の自動処理(ラベル付け・コメント投稿等)は`GITHUB_TOKEN`だけで完結するGitHub Actionsワークフローが担う | 追加のホスティング費用・秘密情報の管理コストがゼロ。既に`ci.yml`等でGitHub Actionsを使っており同じ枠組みの延長で扱える。結果はリポジトリ内(Issueのラベル・コメント等)に残り、権限設定がそのまま説明になる。トレードオフとして、GitHubアカウントを持たないプレイヤーは使えず、即時性や大量アクセスにも向かない |

## 決定(Decision)

**専用のバックエンドを新設せず、GitHub Actions をサーバーの実行基盤として使う。ただし、次の原則を絶対に守る。**

1. クライアント(ゲーム本体)に書き込み権限のある秘密情報を埋め込まない
2. サーバーを叩く操作は、必ずプレイヤー自身のブラウザ操作を起点にする(ゲームが裏で勝手にGitHubへ送信することはしない。`github.com`への遷移・Issue作成といった操作の入口を整えて開くところまでしか行わない)
3. サーバー側(GitHub Actions)は、リポジトリ標準の`GITHUB_TOKEN`だけで完結させる(追加のシークレットを新設・管理しない)
4. 処理結果はリポジトリの中(Issueへのコメント・ラベル・リポジトリ内ファイルへのコミット等)に残す。外部のデータベース・外部APIは新設しない

この基本パターンは次の形になる:

```
プレイヤーの操作(例: バグ報告ボタン)
        │
        ▼
プレイヤー自身のブラウザが github.com 上で操作を行う
(例: 新規Issue作成画面を事前入力して開く。ゲームは関与しない)
        │
        ▼
GitHub側でイベントが発生(例: on: issues: opened)
        │
        ▼
GitHub Actions のワークフローが起動
(GITHUB_TOKEN だけでラベル付け・コメント投稿等の「サーバー処理」を行う)
        │
        ▼
結果はリポジトリの中(Issueのラベル・コメント等)に残る
```

実装例: `src/entities/debugPanel.ts`(`buildDebugIssueUrl`)は、プレイヤーの
端末情報・直近ログをGitHub Issue作成画面のクエリパラメータに詰めた
URLを組み立てて開くだけで、ゲーム側からのHTTP送信は一切行わない。
`.github/workflows/player-report-ack.yml` が`issues: opened`イベントを
起点に`GITHUB_TOKEN`だけでラベル付け等を行う。

なお`plan/playtest-deployment.md`の自動デプロイ(`on: push: branches:
[main]`)や`plan/auto-tester.md`の定期実行テストプレイエージェントの
ように、**プレイヤーの操作を経由せずリポジトリへのイベントだけで
起動するワークフロー**は、原則2の制約と無縁のまま原則3・4に沿って
運用できる。今後サーバー機能を増やす場合は、まずこの「イベント駆動・
非プレイヤー起点」の形にできないかを先に検討する。

## 結果として生じるトレードオフ(Consequences)

- 良い点:
  - 追加のホスティング費用・秘密情報の管理コスト・漏洩リスクがゼロ。
  - 外部SaaSにプレイヤーデータを預けず、すべてがGitHub上で完結する。
    誰が何を見られるかがリポジトリの権限設定そのままで説明できる。
  - 既存のCI基盤(GitHub Actions)の延長で扱えるため、新しい運用知識が
    ほぼ要らない。
- 悪い点:
  - **GitHubアカウントを持たないプレイヤーは使えない。** 一般プレイヤー
    全員を対象にした機能(例: ランキング閲覧)にはそのままでは向かない
    (閲覧だけなら公開リポジトリの内容を静的に読む形で回避できる余地
    はある)。
  - **即時性は求められない。** GitHub Actionsの起動には数秒〜数十秒の
    遅延がありうる。
  - **大量アクセスには向かない。** GitHub Actionsの実行時間・API呼び出し
    回数には上限がある。
  - 「プレイヤー自身がGitHubの画面上で手動操作しなければならない」
    というUX上のトレードオフがある。バグ報告・みんなの記録など複数の
    機能案が、この理由で一部見送られている。
