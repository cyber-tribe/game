# 0016: ゲームルールはドメイン単位のモジュールへ段階的に集約する(DDDの限定導入)

- ステータス: 決定
- 日付: 2026-08-22

## 背景(Context)

`src/game.ts` の `Game` クラスは3,200行超・privateメソッド約100個に達し、
ダイブ状態の保持に加えて、戦闘・タル・仲間・アイテム・レベルアップ・
地域ギミック・ボス・樽比べ・階層進行といった**各ドメインのゲームルール
そのもの**を実装している。問題は `Game` が大きな状態を持つことではなく、
新しいルールを書くとき「とりあえず `Game` に書く」以外の置き場所が
定義されていないことにある。実際、`systems/combat.ts` の
`attackOffsets()` には「特殊効果(会心率・行動遅延)は呼び出し側
(game.ts)で扱う」というコメントがあり、純粋なルールが `Game` へ
漏れ続ける構造が文書化されてしまっている。

一方で、既存設計には守るべき資産がある。

- `GameEvent[]` によるコアとViewの分離(ADR 0002・0013)
- `systems/combat.ts` の `computeDamage()` のような純粋関数のルール
- `Inventory` のように状態と操作が同じモジュールへ集まっている例
- vitest による `tests/` 配下の回帰テスト基盤

## 検討した選択肢

| 案 | 概要 | 評価 |
|---|---|---|
| **現状維持** | 今後も `Game` にルールを足す | `Game` の肥大が続き、ルールの重複・分裂(ADR 0013 で起きた die/checkpoint/recruit の分裂と同型の問題)が加速する |
| **教科書的DDDの全面導入** | 全エンティティのAggregate/Repository化、Value Objectのclass化、1コマンド1UseCase、レイヤー別ディレクトリへの一括移行 | 20K行規模のクライアントゲームには過剰。ダイブ中の状態は全部インメモリでRepositoryに意味がなく、`HitPoint` 等のラッパーclassはTypeScriptの構造的型付けと噛み合わない。一括移行は機能開発を止める |
| **ドメインファーストの段階導入(採用)** | ゲームデザイン上の概念名を持つ純粋TSモジュールへルールを段階的に移す。パターンは必要なものだけ使う | 既存の良い部分(GameEvent境界・純粋関数)の延長線上にあり、移行単位ごとにテストで挙動を固定できる |

## 決定(Decision)

DDDを「classとパターンを増やす手法」としてではなく、次の一文の徹底として導入する。

> ゲームデザイン上の概念とルールを、その概念の名前を持つ純粋な
> TypeScriptモジュールへ集約し、描画・UI・保存などの技術的関心から
> 独立させる。

### 境界と単位

- 最初のBounded Contextは **Dungeon Run**(1回のダイブ)とし、これを
  単一の整合性境界として扱う。Player・Monster・Barrel・Floorは1ターン
  内で強く相互作用するため、最初から細かいAggregateに分割しない。
  境界の細分化は「必ず守るべき不変条件」が明確になってから行う。
- 村・鍛冶・依頼板など `ui/town.ts` 側は Dungeon Run コンテキストの
  **外**であり、本ADRのスコープ外と明示する(将来必要になれば別ADR)。

### ディレクトリの役割分担

レイヤーファーストではなくドメインファーストで `src/domain/` を設け、
既存ディレクトリとの役割を次のように定める。

| 置き場所 | 内容 |
|---|---|
| `domain/<概念名>/` | ゲームルール(純粋関数・型・不変条件を守る操作) |
| `entities/` | 種族・特技・依頼・店などの**静的マスタデータ(カタログ)**。当面ここに残す |
| `application/`(将来) | コマンド進行制御。当面は `Game` がこの役 |
| `view/` `ui/` `audio/` `save/` | 技術的関心。Domainからは参照しない |

「ルールは `domain/`、カタログは `entities/`」を判断基準にする。
移行期間中に「ルールの家が2つある」状態を作らないため、あるドメインを
`domain/` へ移すと決めたら、対応する `systems/` のファイルはそのPRで
`domain/` へ移動する(例: Phase 1 で `systems/combat.ts` →
`domain/combat/`)。

### 実装ルール

1. `Game` をなくすことを目的にしない。最終的にDungeonRunの
   Facade/Application Controllerへ縮小する。
2. ゲーム上の言葉をモジュール名にする(`combat`, `barrel`, `party`,
   `turn` …)。`manager`, `helper`, `util` を安易に増やさない。
3. DomainからThree.js・DOM・Audio・localStorageを参照しない。
4. GameEvent境界(ADR 0002)を維持する。Domain/Applicationが状態変更と
   イベントを生成し、Viewはイベントを再生する。
5. `interface + 純粋関数` もドメインモデルとして認める。状態だけの
   interfaceを無理にclass化しない。`Vec2` や `Dir` もclass化しない。
6. 不変条件を守る必要があるモデルには操作を集約し、状態への書き込みを
   各所から無制限に行わせない。
7. 移行は `Game` のprivateメソッド単位で1つずつ。一括リファクタリングは
   行わない。新機能・仕様変更で触る領域から整理する。
8. ダイブ内部にRepositoryを導入しない(`PlayerRepository` 等は作らない)。
   Repositoryの適用先は永続化境界(`SaveRepository` interface +
   `LocalStorageSaveRepository`)のみ。
9. 数値IDの取り違え防止には、必要に応じて `ActorId` / `BarrelId` /
   `ItemUid` の3つに限ってBranded Typeを使う。それ以上増やさない。
10. 1コマンド1UseCaseクラス方式は採用しない。コマンドごとの処理は
    概念単位のモジュールへ関数として委譲する。

### 挙動の固定方法(移行の前提)

「既存挙動を変えずに抽出」を自己申告にしないため、移行単位ごとに
**GameEventゴールデンテスト**を移行の**前に**書く。守るべき契約は
イベントの種類と順序である(Viewはこの順序に依存して再生する)。

> 同じ乱数シード・同じコマンド列 → 同じ `GameEvent` 列

vitestの既存基盤(`tests/`)をそのまま使う。

### 移行順序

- **Phase 1 — Combatを基準実装にする**: `systems/combat.ts` を
  `domain/combat/` へ移し、戦闘用語と型を明確化。以後、新しい戦闘ルールを
  `Game` に追加しない。
- **Phase 2 — Gameの戦闘“計算”ルールをCombatへ移す**: ダメージ・会心・
  補正・命中判定など純粋な計算に**スコープを絞る**。`Game` の攻撃処理は
  死亡処理・経験値・状態異常付与とターン解決に絡んでおり、「攻撃1回の
  解決フロー全体」の抽出はPhase 4の仕事として明示的に残す(ここを
  混ぜるとPhaseが直列に進まない)。既存の `effectContext(events)` を
  Application層コンテキストの原型として使う。
- **Phase 3 — Barrelドメイン**: 投擲・捕獲・開封・タルわざ・元素タル。
  このゲーム固有のコアドメインなので、Combatで移行パターンを確立した後に
  独立させる。
- **Phase 4 — Turn Resolution**: プレイヤー行動後の処理・敵と仲間の行動・
  状態異常・ターン終了処理など、1ターンの解決ルールをまとめる。
- **Phase 5 — Party / Companion**: 仲間への指示・ゆめわざ・なじみ・
  仲間固有能力。
- **Phase 6 — Dungeon Progression / Floor Rules**: 階層遷移・地域ギミック・
  ボス階・横穴・チェックポイント。
- **Phase 7 — Save境界**: `save.ts`(約1,900行)は規模2位であり、
  スナップショット型を通じてDomainの型変更のたびに影響を受けるため、
  計画の射程内に置く。`SaveRepository` interfaceを切り、セーブ互換
  フィクスチャ(ADR 0009)で回帰を守る。
- **Phase 8 — GameをDungeonRun Facadeへ縮小**: この段階で初めて `Game`
  全体を再評価し、残す責務を決める。

### 置き場所の判断手順

新しいゲームルールを実装するときは次の順で判断する。

1. これはゲームデザイン上、何という概念のルールか?
2. その概念の `domain/` モジュールはあるか?
3. 単一モデルのルールならそのモデル/モジュールへ置けるか?
4. 複数モデルにまたがる純粋なルールならDomain Service相当の関数へ置けるか?
5. ユーザー操作の進行制御ならApplication(当面 `Game`)側か?
6. 描画・音・保存など技術的処理ならDomainの外か?

**「とりあえず `Game` に書く」は選択肢にしない。**

## 結果として生じるトレードオフ(Consequences)

- 新しいルールの置き場所を概念名から判断でき、`Game` に新しいドメイン
  ルールが増え続けなくなる。主要ルールを描画なしでテストできるようになる。
- 移行期間中は `Game` と `domain/` にルールが分散した状態が続く。
  「触るPRで移す + 移すと決めたら旧ファイルは同PRで移動」のルールで
  期間を短くするが、完了までの間、読み手は両方を見る必要がある。
- ゴールデンテストを移行前に書くぶん、個々の移行PRは重くなる。
  そのかわり挙動変化の検出を型チェックとテストに任せられる。
- Branded Type導入時は数値リテラルをIDとして直接渡している既存箇所に
  キャストが必要になる。3つのID型に限定することで影響を抑える。
- DDD用語(Aggregate・Repository等)を限定的にしか使わないため、
  教科書的DDDを期待する読み手には不完全に見える。本ADRがその判断根拠。
