# 0009: セーブデータの後方互換は、削除しないフィクスチャによる回帰テストで守る

- ステータス: 決定
- 日付: 2026-08-12

## 背景(Context)

`src/save.ts` の `loadSave()` は、フィールドごとにサニタイズ関数
(`sanitizeStorage` `sanitizeHut` `sanitizeCompendium` 等)を通し、
壊れた値・存在しない値は初期値へ黙って差し戻す。`JSON.parse` 自体が
失敗した場合も丸ごと `initialSave()` へフォールバックする。この設計は
「壊れた保存データで起動できなくなる」事態は防ぐが、**クラッシュしない
ことは保証しても、「静かにデータの一部が消える」ことまでは防げない。**

`SaveData` は難易度モード・鍛え方・なじみ成長・衣装・命名などの追加で
これまで何度も拡張されてきており、今後もフィールドのリネーム・IDセットの
変更・サニタイズ関数のロジック変更は起き続ける。そのたびに「昔のセーブを
読み込んだら、実は一部の進行状況(図鑑・実績・倉庫の中身等)が黙って
消えていた」という不具合が、テストなしでは検知できないまま入り込みうる。

## 検討した選択肢

| 案 | 概要 | 評価 |
|---|---|---|
| **サニタイズ関数のユニットテストだけで済ませる** | 個々の `sanitize*` 関数を単体で検証する | 関数単体は正しくても、`loadSave()` 全体としてフィールドの組み合わせや呼び出し順序に不具合があるケース(消し忘れ・上書き忘れ)を見落としうる。「過去世代のセーブを実際に読み込んだらどうなるか」という結合された確認にならない |
| **最新の空セーブだけを対象にテストする** | 初期状態の `SaveData` が正しく読み込めることだけを確認する | 「フィールドが値を保っているか」という後方互換の本質を検証できない。空の初期状態はどのフィールドも既定値なので、値が消えても気づけない |
| **過去の主要な節目を模したフィクスチャを複数世代分保持し、削除せず蓄積する** | `tests/fixtures/save/*.json` に、進行が進んだ状態(倉庫にアイテムがある・図鑑が一部埋まっている等)のセーブデータを世代ごとに用意する。各世代について「その世代で存在していたフィールドの値が保持される」「まだ存在しなかったフィールドは `initialSave()` と同じ既定値になる」の両方をassertする | 実際の「古いセーブを読み込む」状況をそのまま再現でき、値が消える不具合を直接検知できる。フィクスチャを削除せず蓄積し続けることで、「一度サポートした世代は今後も互換性を切らない」という前提そのものをテストとして固定できる |

## 決定(Decision)

**`tests/save-compat.test.ts` は、`SaveData` の主要な節目を模した
フィクスチャ(`tests/fixtures/save/v1-initial.json` 以降、現在v8まで)を
`loadSave()` に読み込ませ、(1) その世代で存在していたフィールドの値が
保持されること、(2) まだ存在しなかったフィールドが `initialSave()` と
同じ既定値になること、の両方を確認する。フィクスチャは一度追加したら
削除しない。**

- 対象は拠点の `SaveData`(`loadSave()`)のみ。`loadRunSnapshot()`
  (ダイブ中オートセーブ)は対象外とする。オートセーブは
  `plan/mid-dive-autosave.md` の設計上、「壊れていれば復帰を諦めて
  `null` を返してよい」(1回限りの保証)という方針が既にあり、
  後方互換を保証する対象として扱っていない。
- 新しいフィクスチャを追加するタイミングは、`SaveData` にフィールドを
  追加・変更する実装のたびに1つを目安にする。すべてのコミットを
  追う必要はなく、セーブフォーマットに影響する節目だけで十分とする。
- フィクスチャは手作業でJSONを書いて作る(実プレイからのエクスポートは
  行わない)。既存の `sanitize*` 関数群やカタログ(`ITEMS` `SPECIES` 等)
  を直接参照し、実在するIDだけを使って組み立てる。
- 新規ワークフローは追加しない。既存の `npm test`(vitest)に
  ただのテストファイルとして乗る。

## 結果として生じるトレードオフ(Consequences)

- 良い点:
  - 「古いセーブを読み込んだら進行状況の一部が黙って消えていた」という
    静かな不具合を、実装セッションを跨いだ回帰として機械的に検知できる。
  - フィクスチャを削除しない運用により、「一度サポートした世代への
    互換性を今後も切らない」という約束そのものがテストとして残る。
    後方互換を弱める変更をしたら、意図的に気づける形になる。
- 悪い点:
  - 世代が増えるほどフィクスチャの数・保守コストが増える
    (削除しない方針のため、この増加を止める手段がない)。
  - フィクスチャは手作業で書くため、実際のプレイで生じうる組み合わせを
    網羅しているとは限らない。カバーされていないフィールドの組み合わせに
    起因する互換性バグは、このテストでは検知できない。
  - `loadRunSnapshot()` はこの保証の対象外のままであり、オートセーブの
    保証水準を将来引き上げる場合は別途この方針を見直す必要がある。
