# 0011: 定期実行の自動探索エージェントでまだ知らない不具合を見つける

- ステータス: 決定
- 日付: 2026-08-12

## 背景(Context)

`npm run playtest`(`ci.yml`)は決まった導線を毎回なぞる機械的な回帰
確認で、**既に分かっている操作**が壊れていないかしか確認できない。
一方、プレイヤー自身のGitHub操作を起点にしたバグ報告(`plan/bug-report.md`)・
コミュニティランキング(`plan/community-leaderboard.md`)は、「投稿の
最後の一歩をプレイヤーが手動で行う必要がある」というUX上のトレードオフ
を理由にいずれも廃止した。その結果、**まだ知らない不具合を見つける
自動的な手段が無くなった**。

`design/server-architecture.md` は、プレイヤーの操作を経由せず
リポジトリへのイベントだけで起動するワークフロー(`plan/archive/
playtest-deployment.md` の自動デプロイ等)ならこの制約と無縁でいられる
と示しており、その形での不具合発見手段を検討する必要があった。

## 検討した選択肢

| 案 | 概要 | 評価 |
|---|---|---|
| **`npm run playtest` の固定シナリオを増やしていく** | 決まった導線のテストケースを人手で追加し続ける | 「まだ知らない」不具合、つまり想定していなかった操作の組み合わせは原理的に見つけられない。シナリオの数だけ人手のメンテナンスコストもかかる |
| **プレイヤー起点のバグ報告経路を復活させる** | `plan/bug-report.md` のようにプレイヤー自身のGitHub操作を起点にする | 過去に廃止した理由(投稿の最後の一歩をプレイヤーが手動で行う必要があるUX上のトレードオフ)が変わっていない |
| **定期実行(schedule)される、重み付きランダム入力の自動探索エージェントを新設する** | `tools/auto-tester.mjs` が `npm run playtest` と同じ土台(Playwright + SwiftShader)で、固定シナリオではなく重み付きランダムなキー入力を複数セッション独立に行う。異常を検知したらフィンガープリントで重複排除しつつ `GITHUB_TOKEN` だけでGitHub Issueに起票する | プレイヤーの操作を一切経由しないため、廃止済みの案が抱えていたUX上の制約と無縁でいられる。ランダム性により、人が思いつかなかった操作の組み合わせも探索対象になる。夜間バッチとして継続的に動かせる |

## 決定(Decision)

**`.github/workflows/auto-tester.yml` を毎日1回(JST 3:00)定期実行し、
`tools/auto-tester.mjs` が重み付きランダムなキー入力で8セッション独立に
探索する。異常を検知したら、フィンガープリントによる重複排除を経て
`GITHUB_TOKEN` だけで `auto-report` ラベル付きのGitHub Issueに起票する。**

- **位置づけ**: `npm run playtest`(決まった導線の回帰確認、PRのたびに
  実行)を置き換えるものではなく、両方を維持する。プレイヤーからの
  手動報告経路が無くなった今、このエージェントが唯一の自動的な
  不具合発見手段になる。
- **探索方法**: 各セッション開始時のダンジョン乱数シードと入力選択用
  乱数シードの両方を記録し、見つけた不具合を後から人が再現できるように
  する。1セッションあたり最大200ターンまたは3分の壁時計時間で打ち切り、
  ターン予算の7割を消化したら強制的に次の階へ進める(1回の実行で
  より多くの階層のコンテンツに触れるための効率化)。
- **重複投稿対策**: (1) 同一実行内では同じフィンガープリントから最大
  1回しかAPIを呼ばない、(2) フィンガープリントは発生場所の大まかな
  区分・正規化したエラーメッセージ・スタックトレース最上位フレーム
  (行番号は含めない)から作る、(3) 起票前に `auto-report` ラベルの
  既存Issueを検索し、open中なら24時間に1回だけ再発コメント、
  `not_planned` で閉じられていれば起票しない(人間の判断を覆さない)、
  `completed` で閉じられていれば再オープンしてリグレッションと明示する、
  (4) 1回の実行で新規作成するIssueは最大5件までのサーキットブレーカーを
  設ける。
- **状態の持ち方**: GitHub Actionsの実行自体はステートレスなため、
  「既に見た不具合か」の唯一の正はリポジトリのIssue自体とする。重複管理
  のための追加データベース・追加ファイルは持たない
  (`design/server-architecture.md` 原則4)。
- 追加のシークレットは持たない(`issues: write` 権限の既定の
  `GITHUB_TOKEN` だけで完結、同原則3)。

## 結果として生じるトレードオフ(Consequences)

- 良い点:
  - プレイヤーの手を一切煩わせずに、想定していなかった操作の組み合わせ
    から不具合を継続的に発見できる。
  - フィンガープリント+既存Issue検索+クールダウン+サーキットブレーカー
    の多段防御により、「直っていない不具合を毎回別Issueとして起票し
    続ける」という自動化にありがちな失敗を抑えている。
  - `not_planned` で閉じたIssueを尊重する設計により、人間が下した
    「対応しない」判断をエージェントが勝手に覆さない。
- 悪い点:
  - ランダム入力ゆえに、同じ実行でも毎回異なる範囲しか探索できず、
    網羅性は保証されない(重み付けやターン予算のチューニングに
    継続的な調整が要る)。
  - フィンガープリントの正規化が効かない場合、同じ根本原因が別の
    フィンガープリントとして複数Issue化される可能性が残る
    (サーキットブレーカーで実害の上限は抑えているが、根本原因の
    重複自体は解消しない)。
  - 進行不能(ソフトロック)の疑い検知のような誤検知が起きやすい項目は
    `low-confidence` ラベルで区別しているが、依然として人による
    トリアージが必要。
