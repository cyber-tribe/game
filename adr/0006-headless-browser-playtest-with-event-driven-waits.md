# 0006: 実機動作確認はヘッドレスChromium(SwiftShader)でイベント駆動待ちにより行う

- ステータス: 決定
- 日付: 2026-08-12

## 背景(Context)

ユニットテスト(`src/core` 以下)はゲームロジックを検証できるが、
実際にブラウザで動かしたときにだけ起きる問題(Three.js の初期化失敗、
アセット読み込みの404、DOM操作の例外など)は拾えない。CI で毎回
人手のブラウザ確認をするわけにはいかないため、`tools/playtest.mjs`
が拠点から潜り、歩いて戦ってアイテムを使い、倒れて拠点に戻るまでを
実際に操作し、ページ内で例外や 4xx が出ないことを機械的に確認している。

この自動操作には2つの実務上の壁があった。

1. CI のランナー(および開発コンテナ)には GPU が無く、素の WebGL
   初期化に失敗する。
2. 操作のたびに「アニメーションが終わるまでどれだけ待つか」を
   決め打ちすると、遅い環境では入力が握り潰され、速い環境では
   無駄に待たされる。

## 検討した選択肢

### GPUが無い環境でのWebGL

| 案 | 概要 | 評価 |
|---|---|---|
| **CI をやめて手動確認に頼る** | 実機確認を自動化せず、リリース前に人が確認する | 確認頻度が落ち、PRごとの検証ができない。見落としが増える |
| **GPU付きランナーを用意する** | GPU 搭載のセルフホストランナー等を用意する | 追加の運用コスト・費用がかかる。個人開発の規模には見合わない |
| **SwiftShader によるソフトウェア描画で WebGL を動かす** | Chromium を `--use-angle=swiftshader` 等のフラグで起動し、GPU無しでもWebGLを初期化できるようにする | 追加インフラ不要でCIにそのまま組み込める。ラスタライズをCPUで行うため画素数に比例して遅くなるが、ビューポートを絞れば許容範囲に収まる |

### 操作後の待ち方

| 案 | 概要 | 評価 |
|---|---|---|
| **固定時間(sleep)で待つ** | 各操作のあと一定時間待ってから次に進む | 実装は簡単だが、遅い環境では待ち時間内に処理が終わらず、次の入力が「再生中」として握り潰される。App 側は再生中の入力を捨てる作りのため、これが起きても例外にはならず**静かに失敗する**。実際、足踏み40回のうち10回前後しか実際のターンになっておらず、命名ダイアログが開きっぱなしで以降のキーが全部飲み込まれていた事例がある |
| **`requestAnimationFrame` を待ってから、アプリ側の状態(`debugIdle()`)を見て待つ** | 直前の入力がループに取り込まれたことを rAF 2回で確認し、そのあとアプリ側の「再生中かどうか」のフラグが解けるのをポーリングで待つ | 環境の速さに依存せず、実際に処理が終わったタイミングで次へ進める。App 側に `debugIdle()` というテスト専用の状態参照を1つ追加するだけで済む |

## 決定(Decision)

**CI の実機確認(`npm run playtest`)は、Chromium を SwiftShader
(`--use-angle=swiftshader --enable-unsafe-swiftshader --use-gl=angle
--disable-gpu-sandbox`)で起動し、GPU の無い環境でも WebGL を初期化する。
各操作のあとは固定時間で待たず、`requestAnimationFrame` を2回はさんで
直前の入力がループに取り込まれたことを確認したうえで、
`globalThis.__app.debugIdle()` がアプリ側の再生完了を示すまで
ポーリングして待つ。**

- ビューポートは 800×500 に絞る。SwiftShader は1フレームぶんの
  ラスタライズを丸ごとCPUで行うため、所要時間はほぼ画素数に比例する
  (1280×800から800×500に落として所要時間が大きく縮んだ実測がある)。
  スクリーンショットも各場面1枚(計10枚)に絞る。
- `debugIdle()` は本番のプレイには不要な、テスト専用のデバッグ用
  参照として `src/main.ts` に用意する。

## 結果として生じるトレードオフ(Consequences)

- 良い点:
  - 追加インフラ(GPU付きランナー)無しに、CI で実際のブラウザ操作を
    通した検証ができる。
  - 固定時間待ちで実際に起きていた「入力が握り潰されて何も検査できて
    いないのに気づけない」という静かな失敗を防げる。
  - 環境の速さに依存しないため、CIランナーの性能が変わっても
    タイムアウト値のチューニングをやり直さずに済む。
- 悪い点:
  - `debugIdle()` というテスト専用の参照をアプリ本体
    (`src/main.ts`)に持ち込む必要がある。本番の挙動には影響しないが、
    テストの都合でプロダクションコードに手を入れている。
  - SwiftShader によるソフトウェア描画は実機のGPU描画と完全に同じ
    ではないため、GPU固有の描画不具合(シェーダの互換性等)は
    このテストでは拾えない。
  - ソフトウェア描画は画素数に比例して遅いため、ビューポートや
    スクリーンショット枚数を絞る必要があり、検証できる画面の
    細かさ・網羅性とのトレードオフが常に付きまとう。
