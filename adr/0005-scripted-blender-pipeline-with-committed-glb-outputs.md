# 0005: 3Dモデルは Blender をスクリプトで動かして作り、出力(.glb)を直接コミットする

- ステータス: 決定
- 日付: 2026-08-12

## 背景(Context)

このプロジェクトは「外部から持ってきた素材は一つも使わない」方針
(README参照)のもと、キャラクター・地形・アイテムなどのすべての
3Dモデルを自作している。モデルの作成には Blender の Skin モディファイア
+ サブディビジョンによる有機的なメッシュ生成、アーマチュアの自動
ウェイト付け、5クリップ(待機・歩行・攻撃・被弾・消滅)のキーフレーム
アニメーションなど、GUI 操作を前提とした作業が必要になる。

一方で、このリポジトリの他の部分(`src/`)はコードとして差分管理・
レビュー・CI検証ができる状態を保っており、モデル制作だけがその外に
置かれると、モデルを直したいときの再現性やレビュー可能性が失われる。

## 検討した選択肢

| 案 | 概要 | 評価 |
|---|---|---|
| **Blender の `.blend` ファイルを作業成果物としてコミットする** | 通常のBlender作業フローどおり、GUIで作った `.blend` を保存してコミットする | バイナリファイルのため差分が見えず、レビューができない。「なぜこの形になったか」がコミット履歴に残らない。GUI操作の再現には人が同じ手順を覚えている必要がある |
| **Python スクリプトで Blender (`bpy`) を動かしてモデルを生成し、スクリプトと生成物 (`.glb`) の両方をコミットする** | `tools/models/` 以下に関節位置・太さなどをコードとして書き、`bpy` を Node と同様に実行してビルドする。生成された `.glb` を `public/models/` にそのままコミットする | モデルの形状定義がテキストの差分として見える。形を直したいときはスクリプトを書き換えて再実行すればよく、遊ぶだけの人は Blender 環境が無くても最新の `.glb` をそのまま使える。CI で構造検証(後述 ADR 参照)もできる |
| **`.glb` はコミットせず、ビルド時に毎回生成する** | `public/models/*.glb` をリポジトリに含めず、`npm run build` や CI のたびに Blender で生成する | `bpy` の依存(約1GB)を通常のビルド・開発フローに持ち込むことになり、遊ぶだけの人・通常のWeb開発作業が重くなる。CIも毎回Blenderのセットアップが必要になり大幅に遅くなる |

## 決定(Decision)

**`tools/models/` の Python スクリプトが `bpy`(BlenderのPython API)を
直接動かしてモデルを生成し、出力される `.glb` を `public/models/` に
そのままコミットする。スクリプトと生成物の両方をリポジトリで管理する。**

- キャラクターは関節の位置と太さを定義して Skin モディファイアで
  皮を張り、サブディビジョンで丸める。アーマチュアを自動ウェイトで
  結び、ポーズをキーフレーム化して5クリップを焼き込む。
- `bpy` 5.0 は CPython 3.11 専用のため、通常の Node 環境とは別に
  `tools/setup_blender.sh` で専用の venv を用意する。
- モデルを直したい場合のみ `npm run models` で作り直し、遊ぶだけの
  人はコミット済みの `.glb` をそのまま使うため Blender 環境は不要。

## 結果として生じるトレードオフ(Consequences)

- 良い点:
  - モデルの形状定義(関節位置・太さ等)がテキストの差分として見え、
    レビュー・履歴管理ができる。
  - `bpy` という重い依存(約1GB)を通常の開発・ビルド・CI(モデル系
    以外)から切り離せる。
  - GUI操作の手順を人が覚えておく必要がなく、スクリプトの再実行で
    誰でも同じ結果(後述の非決定性の範囲内)を再現できる。
- 悪い点:
  - `bpy` の出力には非決定性がある。同じマシンで同じスクリプトを
    2回実行しても、頂点数や座標が完全には一致しない(Skin
    モディファイアの位相解決が数値的に不安定なケースがある。
    ツブテガエルを単体で4回作り直したところ 20678 / 21434 / 22490 と
    3通りに割れた例がある)。そのため通常の意味での「差分ゼロなら
    再生成不要」という前提が使えない。`tools/compare_models.mjs` は
    この非決定性を踏まえ、比べられない頂点数・バイト列は無視し、
    メッシュ数・ノード数・クリップ名などの構造と、揺れの影響を
    受けない外形(バウンディングボックス、小数点以下4桁まで一致)
    だけを比較する方式にしている。
  - `.glb` というバイナリ成果物をリポジトリにコミットし続けるため、
    リポジトリサイズが作り直しのたびに増える。
  - スクリプトと生成物の同期はビルド時に自動検証されないため、
    スクリプトを直しても `.glb` の作り直しを忘れると古いまま
    残ってしまう(`tests/models.test.ts` による内容検査で一部は
    検出できるが、形状の反映漏れそのものは検出対象外)。

## 補足: エージェント作業環境でのセットアップ確認(2026-08-13)

このADRを読んだセッションが、事前に `tools/venv` が存在しないことだけを
見て「この環境では `bpy` を使えない(3Dモデル制作は不可能な環境的制約)」
と誤って判断したことがあった。`tools/setup_blender.sh` を実際に実行せずに
結論を出していたのが原因。実際に試したところ、追加のセットアップ操作
なしでそのまま動いたため、手順と実測値をここに残す。

- 実行コマンド: `PYTHON=/usr/bin/python3.11 bash tools/setup_blender.sh`
  (このエージェント作業環境には `/usr/bin/python3.11` が最初から入って
  いた。`python3` が指す既定バージョンと一致しない場合があるため、
  `PYTHON=` で明示するのが安全)
- 所要時間・サイズ: `bpy` のダウンロード・インストールに数分、
  ダウンロード量はスクリプトの事前見積もりどおり約374MB
- 検証: セットアップ後、`tools/venv/bin/python tools/build_models.py
  purun --no-preview` で既存モデルを1体だけ作り直し、エラーなく
  `public/models/purun.glb`(三角形1780、0.3秒)が書き出されることを
  確認した。既存ファイルとバイト列は異なる(前述の非決定性どおり)ため、
  検証後は `git checkout -- public/models/purun.glb` でコミット済みの
  版に戻し、意図しない差分を残さないようにした。
- 結論: **「Blender本体・tools/venv が無い」ことは、この種の環境では
  それ自体が制約ではない。** `tools/setup_blender.sh` を1回実行すれば
  済む(Python 3.11 が使える前提)。新規モンスターの3Dモデルを求める
  plan文書(例: `plan/models/model-*.md`)は、このセットアップを行った上で
  `tools/models/monsters.py` に該当種族の `build_*`/`*_animations` 関数
  を追加し `MONSTERS` に登録する、既存5種と同じ手順で対応できる。
