# 0002: ゲームロジックは描画非依存にし、1ターン分のイベントは同時に再生する

- ステータス: 決定
- 日付: 2026-08-12

## 背景(Context)

このゲームはターン制のローグライクで、プレイヤーの1入力ごとに
「そのターンに何が起きたか」を確定させ、それを画面に反映する必要がある。
確定処理(移動・攻撃・被弾などの判定)と、その結果を見せる処理(補間移動・
モーション・エフェクト)は本来別の関心事だが、素朴に作ると両者が
同じコードの中で絡み合いやすい。

加えて、モンスターの数は仲間システムやモンスターハウスによって
1ターンに数体〜十数体が同時に行動しうる。全員の行動を律儀に
「1体ずつ順番に」見せると、モンスターが増えるほど1ターンの体感時間が
延びてしまい、遊びづらくなる。

## 検討した選択肢

| 案 | 概要 | 評価 |
|---|---|---|
| **判定と描画を一体化する** | 攻撃処理の中で直接 Three.js のモーション再生・カメラ操作まで行う | 実装は素直だが、`src/` のロジックが Three.js / DOM に依存し、Node 上でのユニットテストができなくなる。見た目だけを差し替える(将来のプラットフォーム追加など)ときにロジックごと触ることになる |
| **判定は非依存にし、結果イベントを1体ずつ順番に再生する** | `GameEvent[]` を返す構成にはするが、view 側は先頭から順にアニメーションを消化する | ロジックのテスト容易性は確保できるが、行動する敵の数がそのまま1ターンの体感長になる。仲間・モンスターハウスで登場数が増えるほど悪化する |
| **判定は非依存にし、結果イベントを同時に再生する** | `core`/`dungeon`/`entities`/`items`/`systems` は Three.js にも DOM にも一切依存させず、1ターン分の判定を即座に確定して `GameEvent[]` を返す。view はそれを**同時に**再生する | ロジックのテスト容易性と、体感速度の両方を満たす。同時再生の演出上の工夫(重なる攻撃の見せ方など)は view 側の責務として個別に対応できる |

## 決定(Decision)

**`src/core` `src/dungeon` `src/entities` `src/items` `src/systems` は
Three.js にも DOM にも一切依存しない。プレイヤー入力に対して `game.ts`
がそのターン分の判定を即座に確定し、`GameEvent[]` として返す。
`src/view` はそのイベント列を受け取って**同時に**再生し(移動の補間・
攻撃モーション・被弾表示)、再生が終わった時点で次の入力を受け付ける。**

- 順番にではなく同時に再生するのは、モンスターが増えるほど1ターンが
  長引くのを避けるため。
- 判定側にアニメーションの時間概念を一切持ち込まない。「何が起きたか」
  だけを返し、「どう見せるか・どれだけ待つか」は view 側の責務にする。

## 結果として生じるトレードオフ(Consequences)

- 良い点:
  - `src/core` 以下のロジックは Node 上でそのままユニットテストできる
    (ダンジョン生成・戦闘計算・AI などのテストが Three.js を起動せずに走る)。
  - 見た目(`src/view`)を差し替えても、ゲームの中身(判定ロジック)には
    触らずに済む。将来 Three.js 以外の描画基盤に載せ替える場合や、
    プラットフォームが増える場合の影響範囲を絞れる。
  - モンスターの数が増えても1ターンの体感時間がほぼ一定に保てる。
- 悪い点:
  - 同時に何体もモーションが走るため、演出的に「見づらい重なり」が
    起きないよう view 側で個別に調整が要る(カメラ・エフェクトの
    見せ方など)。
  - 判定確定と結果再生が分離しているぶん、「今何が起きているか」を
    view 側がイベント列から正しく解釈する必要があり、イベントの型
    設計そのものが `core` と `view` の間の暗黙の契約になる。
