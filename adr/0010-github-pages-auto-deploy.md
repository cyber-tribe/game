# 0010: mainマージのたびに最新ビルドをGitHub Pagesへ自動公開する

- ステータス: 決定
- 日付: 2026-08-12

## 背景(Context)

実際に触ってテストプレイするには、これまで `npm install` →
`npm run dev` というローカル環境構築が必要だった。自動化されているのは
`npm run playtest`(ヘッドレスブラウザでの決まった導線の機械的な回帰
確認、CIで毎回実行)だけで、**人が自由に触って試す**手段が整っていな
かった。`design/server-architecture.md` が示す「イベント駆動・非
プレイヤー起点」のワークフロー(原則2の制約と無縁でいられる形)の
3つ目の適用例として、この公開手段を整える。

## 検討した選択肢

| 案 | 概要 | 評価 |
|---|---|---|
| **公開しない(ローカル環境構築を前提のままにする)** | 現状維持 | 触って確かめたい人(自分自身を含む)が毎回環境構築する必要があり、「まず触ってみる」までの敷居が高いまま |
| **PRごとのプレビュー環境を用意する** | PRごとに `https://.../pr-123/` のようなサブパスへデプロイし、PRへ自動でリンクをコメントする | 実装コストが高い(デプロイ先の管理、PRコメントへの書き戻し等)。段階的に広げる余地として残し、まずは効果の大きい方から着手する方が合理的 |
| **mainブランチの最新ビルドを常時1つ、GitHub Pagesへ自動公開する** | `main` への push のたびに `npm run build` し、`actions/upload-pages-artifact` → `actions/deploy-pages` で公開する | 実装コストが最も低く、効果が大きい。静的サイトのホスティングだけなので `design/server-architecture.md` の原則(秘密情報を埋め込まない・追加のシークレット不要)にそのまま沿う |

## 決定(Decision)

**`.github/workflows/deploy-pages.yml` を新設し、`main` への push の
たびに `npm run build` した `dist/` を GitHub Pages
(`https://cyber-tribe.github.io/game/`)へ自動公開する。まずは
mainブランチの最新ビルドを常時1つ公開する段階に留め、PRごとの
プレビュー環境は見送る。**

- `npm run playtest`(既存)を置き換えるものではない。あちらは
  「決まった導線が壊れていないか」を毎回機械的に確かめるためのもので、
  これからも `ci.yml` に残す。こちらは**人間が自由に(スクリプトが
  辿らない経路も含めて)触って試すための入口**という別の役割を持つ。
- `GITHUB_TOKEN` の既定の権限(`pages: write` `id-token: write`)だけで
  完結させ、追加のシークレットは持たない。
- 公開URLはGitHub Pagesの既定ドメインのままとし、カスタムドメインは
  見送る。
- このゲームはサーバーを持たず `localStorage` 完結(`src/save.ts`)の
  ため、公開ビルドで遊んだセーブデータはそのブラウザにだけ残り、
  他の人と混ざったり共有されたりしない。この前提は変えない。

## 結果として生じるトレードオフ(Consequences)

- 良い点:
  - URLを開くだけで誰でも最新のmain相当を試遊できるようになり、
    「まず触ってみる」までの敷居が大きく下がる。
  - 追加のシークレット・外部ホスティング費用なしで実現できる。
  - `ci.yml` とは完全に別のワークフローのため、Pages配信側の問題
    (設定不備等)がPRのマージ判定に影響しない。
- 悪い点:
  - リポジトリ側で GitHub Pages の Source を「GitHub Actions」に
    設定する一度きりの手動操作が必要で、ワークフローファイルの追加
    だけでは自動化できない(リポジトリ設定側の作業が要る)。
  - 常時公開は1系統(main最新)のみのため、レビュー中のPRの内容を
    このURLで確認することはできない(見たい場合はローカル環境構築か、
    将来のPRごとプレビュー環境の追加を待つことになる)。
  - マージ直後は公開ビルドと開発中の内容にわずかな反映ラグが生じる。
