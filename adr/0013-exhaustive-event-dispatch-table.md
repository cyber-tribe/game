# 0013: GameEvent の処理は網羅チェック付き dispatch 表で書く

- ステータス: 決定
- 日付: 2026-08-13

## 背景(Context)

`GameEvent`(core/events.ts)は39種類の判別unionに増えており、それを
消費する側が2箇所ある。

- `view/stage.ts` の `applyEvents`: 見た目・サウンドへの反映。
  `switch (event.type)` で19ケースを個別に処理し、残り20種類は
  `default: break;` で暗黙に無視していた。
- `main.ts` の `submit()`: 記録・進行管理(セーブ・図鑑・依頼板の集計)。
  `if (event.type === "...")` の羅列(13行)で処理していた。しかも
  `die`・`checkpoint`・`recruit` の3種類は、それぞれ処理が2箇所に
  分かれて離れた位置にあった(統合前のコードは同じイベント種別への
  分岐が同じ関数内で2度出てくる状態だった)。

どちらも「新しい `GameEvent` の種別を1つ追加したとき、view側・main.ts側で
処理を書き忘れても、コンパイラは何も教えてくれない」という問題を抱えていた。
`switch` の `default: break;` は「対応不要」と「書き忘れ」を区別できず、
`if` の羅列は網羅性のチェックが効かない。実際に直近の機能追加
(サウンド再生・スクリーンリーダー対応・設定画面など)のたびに、
どちらかの箱への反映が漏れていないかを目視で確認する必要があった。

## 検討した選択肢

| 案 | 概要 | 評価 |
|---|---|---|
| **現状維持(switch + if羅列)** | 今後も同じ形で処理を足していく | 種別が増えるほど「書き忘れても気づけない」リスクが増す。die/checkpoint/recruitのような分裂も今後また起こりうる |
| **`{ [K in GameEvent["type"]]: (event) => R }` 形のマップ型 dispatch 表にする** | イベント種別ごとの処理を1つのオブジェクトリテラルにまとめ、マップ型で「全種別ぶんのキーが無ければ型エラー」を強制する。見た目・サウンドに影響しない種別は `noop` として明示する | 新しい種別を追加すると、この表に対応するキーを書くまでtypecheckが通らなくなる。「対応不要」は `noop` という形で明示され、書き忘れとは区別できる。呼び出し側での `handlers[event.type]` の取り出しにはインデックスアクセス1箇所だけ型アサーションが要るが、オブジェクトリテラルを書く側は各キーの値が `Extract<GameEvent, {type: K}>` に絞り込まれた状態でチェックされるので安全 |

イベントバス的な仕組み(サブスクライバー登録など)の導入も一瞬検討したが、
`GameEvent[]` を1ターンぶんまとめて再生する既存の設計(ADR 0002)自体は
健全であり、「種別ごとの処理をどう書くか」という粒度の問題でしかない
ため見送った。

## 決定(Decision)

**`view/stage.ts` の `applyEvents` と `main.ts` の `submit()` を、
`{ [K in GameEvent["type"]]: (event: Extract<GameEvent, {type: K}>) => R }`
という形のマップ型を持つ dispatch 表に書き換える。**

- `view/stage.ts`: `buildEventHandlers(floor, scale)` が
  `StageEventHandlers`(戻り値はロック秒数)を返す。見た目・サウンドに
  影響しない20種類(`miss`・`spawn`・`status`・`recruit`・`gameOver`等)は
  `noop`(`() => 0`)として明示した。
- `main.ts`: `buildSubmitEventHandlers()` が `SubmitEventHandlers`
  (戻り値はvoid)を返す。以前2箇所に分かれていた `die`・`checkpoint`・
  `recruit` の処理は、それぞれ1つのハンドラに統合した。統合後の
  ハンドラ内の実行順は、統合前のソース上の並び順をそのまま保っている。
- どちらも `handlers[event.type]` で対応する処理を引く。マップ型の性質上
  この1箇所だけは `as (event: GameEvent) => R` という型アサーションが
  必要になる(`event.type` という非リテラル値でのインデックスアクセスは
  TypeScriptが自動では絞り込めないため)。表を書く側(オブジェクトリテラルの
  各プロパティ)は絞り込まれた型でチェックされるので、安全性の大半は
  こちらで担保される。

## 結果として生じるトレードオフ(Consequences)

- 良い点:
  - `GameEvent` に新しい種別を追加すると、`view/stage.ts` と `main.ts`
    の両方でこの表に対応するキーを書くまでtypecheckが通らなくなる。
    「対応不要」と「書き忘れ」が型エラーの有無で区別できるようになった。
  - `main.ts` 側で同じイベント種別への処理が離れた場所に分裂する
    (die/checkpoint/recruitのような状態)ことが構造的に起きなくなった
    (1種別=1エントリなので、同じキーを2度書けばオブジェクトリテラルの
    重複プロパティとして目に見える)。
  - `view/stage.ts` はロック秒数の計算がswitch文の`lock = Math.max(lock, ...)`
    という副作用の積み重ねから、各ハンドラの戻り値を`Math.max`で畳み込む
    形になり、「このイベント種別が何秒ロックするか」が1箇所で完結して読める。
- 悪い点:
  - `handlers[event.type]` の呼び出し側で型アサーションが1箇所ずつ
    (計2箇所)必要になる。TypeScriptの型システムの制約(非リテラル値での
    マップ型インデックスアクセスを自動では絞り込めない)によるもので、
    完全に型安全とは言えない部分が残る。
  - `noop` エントリの羅列は、対応する種別が本当に「意図的に無視している」
    のか、まだ実装していないだけなのかを、コード上で区別する手段が無い
    (コメントで個別に説明するかは今後の運用次第)。
