# サーバー基盤方針(GitHub Actions)

これまでこのゲームはサーバーを持たず、`localStorage` だけで完結する
前提で多くの文書を書いてきた(`design/yorishiro-moods.md` 等)。それは
「サーバーを持たない設計にする」という決定ではなく、**単に今のところ
サーバーが無いという現状の観測**に過ぎなかった。ここからは実際に
サーバー機能を用意していく。第一弾として、**GitHub Actions をサーバーの
実行基盤として使う**方針を定める。

## なぜ GitHub Actions か

- 追加のホスティング費用・運用の手間がかからない。このリポジトリは
  既に `ci.yml` `models.yml` で GitHub Actions を使っており、同じ
  枠組みの延長で扱える。
- README にある「外部から持ってきた素材は一つも使っていない」
  「すべて自作」という姿勢と相性がよい。外部のSaaSにデータを預けず、
  リポジトリの中で完結させられる。
- 小規模なプロジェクトの最初のサーバー機能としては十分な処理能力を持つ
  (常時起動ではなく、イベント駆動で必要なときだけ動く)。

## 絶対に守る原則

### 1. クライアント(ゲーム本体)に書き込み権限のある秘密情報を埋め込まない

ブラウザで動く以上、クライアントのコードは誰でも読める。GitHubへの
書き込み権限を持つトークン(Personal Access Token 等)を一切埋め込まない。
埋め込めば、抜き出されて他人に悪用される(リポジトリへのスパム投稿等)
リスクを常に抱えることになる。

### 2. サーバーを叩く操作は、必ずプレイヤー自身のブラウザ操作を起点にする

ゲームクライアントが裏で勝手にGitHubへ何かを送信することはしない。
`github.com` への遷移・Issue作成といった操作は、**プレイヤー自身の
GitHubアカウントで、プレイヤー自身が起こす**。ゲームは「その操作の
入口を整えて開く」ところまでしか行わない。この原則により、秘密情報を
持たなくてもGitHub側の操作(Issue作成等)が成立する。

### 3. サーバー側(GitHub Actions)は、リポジトリ標準の `GITHUB_TOKEN` だけで完結させる

ワークフロー実行のたびに自動発行される、そのリポジトリだけに効く
一時トークン(`secrets.GITHUB_TOKEN`)を使えば、ラベル付け・コメント
投稿等はまかなえる。**追加のシークレットを新設・管理しない**ことを
基本方針にする(管理コストと漏洩リスクの両方を避ける)。

### 4. 処理結果はリポジトリの中に残す

外部のデータベース・外部APIを新設せず、Issueへのコメント・ラベル・
(必要であれば)リポジトリ内のファイルへのコミットとして結果を残す。
すべてがGitHub上で完結し、誰が何を見られるかがリポジトリの権限設定
そのままで説明できる。

## 基本パターン

```
プレイヤーの操作(例: バグ報告ボタン)
        │
        ▼
プレイヤー自身のブラウザが github.com 上で操作を行う
(例: 新規Issue作成画面を事前入力して開く。ゲームは関与しない)
        │
        ▼
GitHub側でイベントが発生(例: on: issues: opened)
        │
        ▼
GitHub Actions のワークフローが起動
(GITHUB_TOKEN だけでラベル付け・コメント投稿等の「サーバー処理」を行う)
        │
        ▼
結果はリポジトリの中(Issueのラベル・コメント等)に残る
```

適用例は `plan/community-leaderboard.md` のみんなの記録投稿(Issue作成→
検証・記録更新)。今後サーバー機能を増やす場合も、まずこのパターンに
当てはめられないかを検討する。

## この方針の限界(正直に書いておく)

- **GitHubアカウントを持たないプレイヤーは使えない。** この方針は
  「プレイヤー自身の操作でGitHub上の操作を行う」ことが前提のため。
  一般プレイヤー全員を対象にした機能(例: ランキング閲覧)には
  そのままでは向かない。閲覧だけなら公開リポジトリの内容を静的に
  読む形(GitHub Pages等)で回避できる余地はあるが、本文書の対象外。
- **即時性は求められない。** GitHub Actionsの起動には数秒〜数十秒の
  遅延がありうる。リアルタイム性が必要な機能には向かない。
- **大量アクセスには向かない。** GitHub Actionsの実行時間・API呼び出し
  回数には上限がある。多人数が同時に使う可能性のある機能は、この
  パターンで作る前に上限を確認する。
