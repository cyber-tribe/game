> **実装済み。** `tools/audio/similarity.ts`(新規、純粋関数のみ)に
> `harmonicFingerprint`(曲を相対位置で16区間に割り、区間ごとにペンタト
> ニック3オクターブ分のエネルギーをGoertzelアルゴリズムで求めて連結した
> ベクトル)・`timbreFingerprint`(対数間隔24点のスペクトル重心・
> フラットネス・ゼロ交差率)を実装した。
>
> **設計変更(較正実験で判明)**: 当初案は「和声・音色の**両方**が閾値内の
> ペアだけを似すぎと判定する」(誤検知を避けるねらい)だったが、実際に
> 1回目・2回目の所見状態を再現して較正すると、コード進行の退行で近づく
> ペアと楽器編成の退行で近づくペアはほぼ別の組み合わせで、両方同時を
> 要求すると2つの所見をどちらも検知できなかった。1回目・2回目はそもそも
> 別々の原因(別々のPR)だったので、**軸ごとに独立して**閾値を超えたら
> 検知する設計に変更した(`findTooSimilarPairs`、`reasons`にどちらの軸か
> を記録)。誤検知の許容は「`npm run audio`では警告に留めビルドは
> 止めない」という当初案どおりの運用で吸収する。
>
> 和声フィンガープリントも、当初案(曲全体の単純な時間平均)では
> コード進行を全曲共通に戻しても曲間の類似度がほとんど動かなかった
> (時間平均は「どの音がどれだけ使われたか」のヒストグラムにしかならず、
> 進行の**順序**を捨ててしまうため)。区間に割って連結する方式に変えて
> 初めて、退行時に類似度が明確に(現行の平均約0.33→退行時average約0.62
> ...のように)上がるようになった。
>
> **較正実験の実測値**(`bars`は各specの本来値、対象はvillage・region1〜8・
> boss・true-awakening、pairwise cosine類似度・Euclidean距離、単位はいずれも較正実験内でのみ意味を持つ相対値):
> - 現行(両修正後)の和声類似度: 最大0.488(閾値0.5未満、0件も超えない)
> - 完全退行時の和声類似度: 6ペアが0.5以上(最大0.625)
> - 現行の音色距離(zスコア正規化後): 最小0.283
> - 完全退行時の音色距離: 最小0.207
>
> 閾値は`harmonicSimilarityThreshold=0.5`・`timbreDistanceThreshold=0.25`
> とした(現行状態を1件も誤検知せず、完全退行状態は複数ペアを検知する
> 実測値の間に設定)。`tools/audio/build.ts`の`npm run audio`末尾に
> 組み込み、`tests/audio-similarity.test.ts`(新規7件)で1回目・2回目
> それぞれの所見状態の再現による方向性の検証と、現行11本が0件・
> 完全退行させた11本が1件以上検知されることを確認する。
>
> **検証**: `npx tsc --noEmit`・`npx vitest run`(136ファイル/1763件)・
> `npm run build`・`npm run audio`(似すぎ警告0件、生成される`.wav`に
> 差分なし)いずれも成功。
>
> **限界**(計画書の対象外どおり): 個別の1ペアだけを退行させた場合の
> 検知率までは較正していない(全体を退行させた場合の検知は確認済み)。
> 「曲としての魅力」等の主観判定は引き続きユーザー本人の聴感評価に委ねる。

# BGMの「似すぎ」を人手を介さず機械的に検知する

## 経緯

`plan/sound/bgm-listening-review-findings.md`の2回の所見(「どれも同じに
聴こえる」「全部が和の雰囲気」)は、いずれも実装セッション(テキストベース
のAIで音声を知覚できない)ではなく**ユーザー本人が実際に聴いて**初めて
発覚した。この運用(実装セッションが仕様書を書き実装し、ユーザーが
ヘッドホンで聴いて所見を伝える)自体は今後も続ける前提だが、今回の2件は
どちらも「構成上の手抜き」(全曲共通のコード進行、全曲同じ4種の楽器の
重みづけだけの差別化)という**機械的に検知できる種類の退行**だった。
将来同種の退行(誰かが`chordSkeleton`を指定し忘れる、`weights`を
安易にコピペする等)が起きても、次にユーザーが聴くまで気づけないのは
避けたい。そこで、音楽性そのものの判定はできなくても、**この2つの
既知の失敗パターンへの逆戻りだけは音を聴かずに検知できる**仕組みを作る。

## 変更内容

### 1. 和声フィンガープリント(「どれも同じ」の再発を検知する)

合成音源であり、鳴っている音の対象周波数(ペンタトニック各度数×
複数オクターブ、15点程度)はあらかじめ既知なので、汎用FFTを実装せず
**Goertzelアルゴリズム**(狙った周波数だけのエネルギーを直接計算できる、
FFTより単純)で各対象周波数のエネルギーを時間窓ごとに求め、曲全体で
時間平均して正規化したベクトルを得る。

`tools/audio/similarity.ts`(新規、純粋関数のみ、ファイルI/Oなし)に
`harmonicFingerprint(samples: Float32Array, sampleRate: number): number[]`
として実装し、BGM同士の総当たりでコサイン類似度を計算する。

### 2. 音色フィンガープリント(「全部が和の雰囲気」の再発を検知する)

スペクトル重心(明るさ)・スペクトルフラットネス(倍音性かノイズ性か)・
ゼロ交差率・アタック時間(立ち上がりの速さ)を曲全体で時間平均する。
mallet/flute/gong/bow/rattle等、音色が実質的に異なれば、これらの数値も
はっきり異なるはず。

同ファイルに`timbreFingerprint(samples: Float32Array, sampleRate: number):
number[]`として実装し、曲間のユークリッド距離を計算する。

### 3. 判定・キャリブレーション・組み込み

- 1回目の所見の状態(`chordSkeleton`を指定せず全曲`CHORD_SKELETON`
  共通)を`git stash`等で一時的に再現し、`harmonicFingerprint`の
  曲間類似度が実際に高くなることを確認する(閾値を決める根拠、
  いわば負の対照実験)。
- 2回目の所見の状態(`gong`/`bow`/`rattle`の重みを全部0に戻す)を
  同様に再現し、`timbreFingerprint`の曲間距離が実際に近くなることを
  確認する。
- 上記2実験で求めた閾値をもとに、`isTooSimilar(a, b): boolean`
  (和声・音色の両方が閾値以内に収まっているペアだけを「似すぎ」と
  判定する。どちらか一方だけ近くても、地方ごとの意図的なテンポ・
  拍子の共通性等はあり得るため誤検知にしない)を実装する。
- `tools/audio/build.ts`(`npm run audio`)の末尾で、生成した
  BGM11本(村・第一〜第八地方・ボス・真の目覚め。他6曲は対象外の
  聴感評価と同じ範囲に揃える)の全ペアをチェックし、「似すぎ」が
  あればコンソールに警告を出す(ビルド自体は失敗させない。閾値の
  確信度がまだ低いため、まずは目視で気づける警告に留める)。
- `tests/audio-similarity.test.ts`(新規)に、現行の`BGM_SPECS`
  全曲の総当たりチェックを追加し、「似すぎ」ペアが0件であることを
  CIで継続的に検証する(退行があればテストが落ちる)。

## 受け入れ基準

1. 1回目の所見の状態を再現すると、`harmonicFingerprint`の類似度が
   現行(修正後)より明確に高くなることを確認できる。
2. 2回目の所見の状態を再現すると、`timbreFingerprint`の距離が
   現行(修正後)より明確に近くなることを確認できる。
3. 現行のBGM11本では、全ペアが`isTooSimilar`でfalseになる。
4. `npm run audio`実行時、似すぎペアがあればコンソールに警告が出る。
5. `tests/audio-similarity.test.ts`が現行の構成に対して緑になり、
   1回目・2回目の所見状態を模したケースでは意図的に赤くなる
   (退行検知が機能することそのものをテストする)。

## 対象外

- 「曲としての魅力」「メロディの覚えやすさ」「初めて聴く民謡らしさ」等、
  主観的な音楽性の判定(`bgm-listening-review.md`の5項目のうち、
  数値化できない項目はこれまでどおりユーザー本人の聴感評価に委ねる。
  本仕組みは「構成上の手抜きへの回帰」を防ぐことだけが目的で、
  聴感評価を代替・省略するものではない)
- SFX・ジングルへの適用(BGM11本の「どれも同じ」問題への対応に限定する)
- 汎用FFTライブラリの導入(対象周波数が既知なためGoertzelで十分。
  将来ノイズ主体の楽器(rattle等)の音色フィンガープリントの精度を
  上げたくなった場合は別途検討)

## 未決事項

- 類似度・距離の具体的な閾値(実測してから確定する。上記「判定・
  キャリブレーション」の対照実験の結果次第で調整する)
- `npm run audio`の警告を、将来的にビルド失敗(CIを落とす)レベルまで
  厳格化するかどうか(まずは警告に留め、閾値の安定性を見てから判断する)
- 音色フィンガープリントの特徴量(スペクトル重心等の4種)で
  `gong`/`bow`/`rattle`を十分に判別できない場合、特徴量を追加するか
  (実装しながら調整する)
