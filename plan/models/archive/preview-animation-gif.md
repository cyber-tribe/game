# モデルプレビューをGIF化し、アニメーションまで確認できるようにする

## 経緯

`engine-preview-snapshots.md`(実装済み)は `tools/preview/<名前>.png`
を1体1枚の静止画で持つ。`attack=1` クエリで攻撃モーションの
特定フレームを焼くだけで、**歩行・被弾・消滅を含む一連の動きは
GitHub上で確認できない**。動きの品質(タメ・ツメ・二次揺れ、
`toon-advanced-techniques.md` のスメア・ヒットストップ等)は
静止画では判断できないため、GIFへ切り替える。

## 変更内容

### 1. 1体1ファイルのまま、静止画からGIFへ差し替える

ファイル数を増やさない(現状の運用方針を継続する)。
`tools/preview/<名前>.png` を `tools/preview/<名前>.gif` に置き換え、
**そのモデルの全クリップを順番に繋いだ1本のループ**にする:

```
idle(1.5秒)→ walk(1.5秒)→ attack(1回)→ hit(1回)→ die(1回)→ idle に戻る
```

- クリップが存在しないモデル(静止物・非スキンメッシュ)は、
  従来どおり静止画(1フレームのPNG、または1フレームだけのGIF)で
  よい。
- die の終わりで待たず即座に idle から再生し直す(死亡→復活を
  自然な区切りとして許容する。プレビュー用途なので違和感より
  ループの分かりやすさを優先する)。

### 2. 撮影方法(`tools/preview-harness.ts`/`preview_engine.mjs` の拡張)

- ハーネス側: `AnimationMixer` を実時間ではなく**固定Δtで手動更新**
  するモードを追加する(`mixer.update(1/12)` のように、狙った
  フレームレートぶんだけ進めてから1枚描画、を繰り返す)。実時間
  任せだとヘッドレス環境の描画間隔が不安定でコマ数が揃わない。
- 各フレームは `canvas.toDataURL()` でページ内から直接取り出し、
  base64の配列としてNode側へ返す(Playwrightの `page.screenshot()`
  をフレーム数ぶん呼ぶより高速。1回のページ読み込みで全フレームを
  取り切る)。
- Node側(`preview_engine.mjs`)で、集めたフレーム配列を
  GIFへエンコードする。エンコードライブラリはネイティブビルドを
  要求しない純JS/WASM実装を選ぶ(CI環境での追加セットアップを
  避けるため。具体的なパッケージ選定は実装時に決める)。

### 3. 軽量化(確認用途なので画質より軽さを優先する)

- 解像度は現行の512×512から**256×256へ落とす**(確認用途で
  十分。ファイルサイズを抑える)。
- フレームレートは**12fps**を既定にする(動きの緩急は分かるが
  データ量は抑えられる)。
- 減色(GIFの256色パレット)はそのまま許容する(トゥーンの平坦な
  塗りと相性がよく、劣化が目立ちにくい)。
- 1体あたりのファイルサイズの目安を試作段階で計測し、リポジトリの
  合計サイズが無視できない増分にならないか確認する(67種+建物+
  村人。増えすぎる場合はループの長さを短縮する、フレームレートを
  さらに落とす等で調整する)。

### 4. README・CIへの反映

- `tools/preview/engine/README.md` の生成テンプレートを、PNG参照から
  GIF参照に差し替える(GitHubはmarkdown内の `.gif` をそのまま
  アニメーション表示する)。
- `models.yml` の自動コミットフローは変更不要(対象拡張子が
  `.png` から `.gif` に変わるだけ)。CI実行時間は、フレーム数ぶん
  描画コストが増える(1体あたり従来の1枚→数十枚)ため、
  全体の所要時間を計測し、大きく伸びるようなら差分モード
  (変更のあった glb だけ撮り直す。`engine-preview-snapshots.md`
  未決事項に既にあった案)を今回あわせて実装する。

## 受け入れ基準

1. GitHub上で `tools/preview/engine/README.md` を開くと、各モデルの
   GIFがアニメーションして表示され、idle・walk・attack・hit・die
   の一連の動きが確認できる。
2. スメア・ヒットストップ・タメツメ・二次揺れなど、動きに関わる
   実装の変更が、静止画では分からなかったがGIFでは分かる
   (実例として、まばたき実装後のモデルで瞬きが確認できることを
   1体で検証する)。
3. 1体あたりのファイルサイズが常識的な範囲(数百KB程度)に収まる。
4. `npm run preview-engine`(既存コマンド)がGIF出力後もCIの
   所要時間を大きく延ばさない(差分モードで対応する場合はそれを
   含めて確認)。

## 対象外

- 個別クリップごとの複数GIF出力(1体1ファイルの方針を維持する)
- 高フレームレート・高解像度化(確認用途に不要)

## 未決事項

- GIFエンコードに使うライブラリの具体的な選定
- リポジトリサイズの増分が大きい場合の対処(ループの短縮/
  フレームレート引き下げ/差分モードの3択。実測してから決める)
- die終わりから即idleへ戻る継ぎ目の見え方(気になるほど不自然なら
  1〜2フレームのクロスフェード相当を検討する)

## 実装状況

全109モデル(アニメーション付き77体+静止物32個)に適用し、実装した。

- **1. 静止画からGIFへの差し替え**: 実装済み。`tools/preview-harness.ts`
  が`idle(1.5秒)→walk(1.5秒)→attack→hit→die`の順にActorViewを
  再生し、クリップを持つモデルだけGIFにする(クリップの無い静止物・
  非スキンメッシュは従来どおりPNGのまま。`preview_engine.mjs`が
  出力先を判定し、モデルが切り替わった側の古いファイル(.png⇔.gif)を
  消す)。die終わり→idle再開の継ぎ目は、実際に生成したGIFを確認した
  限り違和感が無く、クロスフェードは見送った。
- **2. 撮影方法**: 実装済み。`AnimationMixer`を`view.update(1/12)`で
  固定Δt更新し、毎ステップ`gl.readPixels`で直接ピクセルを取得する
  (`canvas.toDataURL`のフレーム数ぶん呼び出すより高速。WebGLの
  readPixelsは行順が逆なので上下反転してから使う)。GIFエンコードは
  **ブラウザ側**(`preview-harness.ts`)で完結させ、`preview_engine.mjs`
  へはbase64の完成品を1回だけ渡す設計にした(フレームごとの生ピクセル
  配列をNode側へ転送するより通信量が桁違いに少ない)。
- **エンコードライブラリ**: `gifenc`(ネイティブビルド不要な純JS実装、
  約200KB)を選定し devDependencies に追加した。型定義が無い
  (`@types/gifenc`も存在しない)ため、実際に使う関数だけの最小限の
  型を`tools/gifenc.d.ts`に書いた。
- パレットは先頭フレームだけでなく、全フレームを間引いてサンプリング
  した合成データから作る(被弾フラッシュ等、一部のクリップにしか
  出ない色が量子化から漏れるのを防ぐ)。
- **3. 軽量化**: 実装済み。解像度256×256・12fps・GIF標準の256色
  パレット(実際は128色に制限)。実測: 平均約266KB/体、最大約590KB
  (`yorishironozankyo`)で、受け入れ基準3の「数百KB程度」に収まった。
  `tools/preview/`ディレクトリ全体では約3.7MB→約21MBに増えた
  (リポジトリサイズの増分としては軽くはないが、差分モードを
  今回は実装せず許容する判断とした。増分が問題になった場合は
  未決事項に残る3択で対処する)。
- **4. README・CIへの反映**: README生成はモデルごとの実際の拡張子
  (.gif/.png)を参照するよう修正済み。`models.yml`(CI連携)は
  `engine-preview-snapshots.md`アーカイブ時点で見送り方針のまま
  変更していない(手元で`npm run preview-engine`を実行する運用を継続)。
  全モデルの撮影は実測`4分39秒`(旧: 静止画のみで数十秒程度)。
  CIジョブとして自動実行する運用は無いため受け入れ基準4の
  「CIの所要時間」への影響は未計測。差分モード(変更のあった
  glbだけ撮り直す)は今回実装しなかった(スコープ外として残す)。
- 対象外だった項目(個別クリップごとの複数GIF・高フレームレート化)
  には手を付けていない。
