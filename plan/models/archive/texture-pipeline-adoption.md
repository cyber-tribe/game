# 頂点カラーオンリー方針を終え、全アセットにテクスチャを導入する

## 経緯

`ps2-quality-adversarial-review.md` の分岐点1(テクスチャレス方針の
是非)で「全面解禁」を選んだ。全キャラクター・建物・地形タイルに
実測相当のテクスチャ運用を導入し、ポリゴン予算も実測値へ
下方修正する。本書はその実行仕様であり、
`plan/models/archive/visual-quality-uplift.md` 施策Aのポリゴン予算表
(15,000〜30,000等)を、下記の新しい表で置き換える(supersede)。

## 変更内容

### 1. 頂点カラーオンリー方針の終了

`tools/models/common.py` の `bake_ao_to_vertex_colors()` を軸にした
頂点カラーのみの方針を終了し、UV展開+テクスチャを全モデルの標準
工程にする。ただし**「アセットはコードから生成する」方針は維持する**。
外部のペイントソフトで描いた画像ファイルを持ち込むのではなく:

- 既存の頂点カラー技法(AOベイク・上下グラデーション・
  `shade_tint`/`highlight_tint`による色相シフト)は、**ベイク先を
  カラー属性からテクスチャ(Image Texture)に変えるだけで大部分が
  再利用できる**。ゼロからの作り直しではない。
- 模様・生地の織り目・鎧の刻印・傷等の描き込みは、Blenderの
  シェーダーノード(ノイズ・ボロノイ・ブリック等の手続きノード)を
  組んでベイクする。
- ドット的な塗り分けが必要な部位(目の光彩の柄、徽章等)は、
  Python側でピクセル配列を直接組み立てて `bpy.data.images` に
  書き込む(外部画像ツール不要)。

### 2. テクスチャの規模

実測(1体あたりテクスチャ5枚前後、1枚128〜256px)に合わせる。
当時のハードのようなパレット減色(CLUT)は必須にしない(現在の
GPUに制約は無い)が、トゥーンの4階調シェーディングと喧嘩しないよう、
テクスチャ側もなだらかな微細グラデーションではなく「面ごとに一段」
寄りの塗りにする。

目安: 肌・服・目・小物・専用の5枚前後。すべてのモデルが5枚を
使い切る必要はなく、単純な種族は2〜3枚でよい。

### 3. ポリゴン予算の全面的な下方修正

実測値に基づき、`archive/visual-quality-uplift.md` 施策Aの表を
以下に置き換える:

| 対象 | 新予算 | 根拠 |
|---|---|---|
| ガルド・村人 | 4,000〜7,500(顔に1,000前後を配分) | 実測の人型主人公(全身5,700、うち顔1,200)を基準に、詳細はテクスチャに預けポリゴンで肩代わりしない |
| モンスター(通常) | 1,200〜5,000(体格比例) | 一般的な基準(2,000〜10,000)の下寄り。ダイブ中に多数同時出現するため軽い方に寄せる |
| 地方ボス | 6,000〜16,000 | 画面いっぱいの巨大ボスの実測(10,000〜16,000)に準拠 |
| タル・小道具 | 800〜2,000 | 手に取る頻度は高いが画面占有は小さい |
| 建物 | 1,500〜4,000 | 住居スケールの実測相当 |
| 地形タイル | 300〜800 | インスタンシング前提。枚数が多いため実測よりさらに絞る |

**現行のガルド(直近の再デザインで7,400tri)は新予算の上限にほぼ
収まっている。ポリゴン数そのものの作り直しは不要**で、追加作業は
UV展開とテクスチャ化のみでよい。

### 4. 造形パイプラインへの変更(`tools/models/common.py`)

- `build_skinned()` の出力にUV展開のステップを追加する(Smart UV
  Project相当。継ぎ目は関節の位置に集中させ、引き伸ばしを抑える)。
- `bake_ao_to_vertex_colors()` を、ベイク先をテクスチャにした
  `bake_ao_to_texture()` へ拡張する(頂点カラー版は小物など
  UV展開が不要なものにまだ使えるなら並存させてよい)。
- `make_material()` にベースカラーテクスチャのスロットを持たせる。
- `export_glb()` の書き出しを、頂点カラー一本槍から、テクスチャ+
  UV座標も含める形に変える。

### 5. 描画側(`src/view/assets.ts`)への影響

`toToonMaterial()` は既に `std.map`(テクスチャ)を引き継いでいる。
`hasVertexColors` の判定・`vertexColors` フラグが、テクスチャ主体の
モデル(頂点カラーを持たない)で誤動作しないことを確認する程度で、
大きな変更は不要な見込み。

## 展開順

全67種+建物+地形タイルの一斉移行はしない。

1. **ガルド**を最初の適用対象にする。形状は直近の再デザインのまま、
   UV展開+テクスチャ化のみ行う(新旧比較スクリーンショットを
   PRに添付)。
2. 続けて `character-design-language.md` が元々定めた展開順
   (ぷるん→地方ボス8体→村人)を踏襲し、その後モンスター全種→
   建物→地形タイルへ広げる。

## 受け入れ基準

1. ガルドがUV展開+テクスチャで再書き出しされ、頂点カラーオンリーの
   ときと同等以上の見た目品質になる(新旧比較スクリーンショット)。
2. `tools/models/common.py` のAO・色相シフトの技法が、頂点カラーで
   なくテクスチャベイクとして動作する。
3. モバイル実機で60fpsを維持する。テクスチャメモリの増分を計測し、
   シーン合計の予算管理(ダンジョン・村の予算)にテクスチャ容量も
   含める。
4. 新しいポリゴン予算表が `plan/models/sheets/` の各デザインシートの
   前提として以後参照される。

## 対象外

以下は本書の分岐(テクスチャ方針)とは別の決定が必要なため、
`ps2-quality-adversarial-review.md` の指摘のうち本書では扱わない:

- まばたき・視線移動の実装(同レビュー重大4)
- 3灯規律のシーン間統一(同 中程度5)
- 二次揺れの遅延フレーム数の全キャラ共通規律化(同 中程度6)
- `build_skinned()` に硬い形状の部品を組み込むシルエット改善
  (同 重大3。テクスチャで色の境界は付けられるようになるが、
  肩当ての段差のような形の境界は別途の造形作業が要る)

## 未決事項

- テクスチャの生成手段を「Blenderのプロシージャルノードをベイク」
  「Python側でピクセル配列を直接書く」のどちらに主軸を置くか
  (両方使い分けてよいが、`common.py` の共通関数は実装時に試して
  決める)
- パレット減色(CLUT相当)の採用可否(見送ってもよいが、トゥーンとの
  調和を一度エンジン内プレビューで試写して判断する)

## 実装状況

展開順1(ガルド)のみパイロットとして実装した。展開順2(ぷるん→
地方ボス→村人→モンスター全種→建物→地形タイル)は今回のスコープ外。

- **1・4. 頂点カラーオンリー方針の終了・造形パイプライン**: 実装済み。
  `common.py` に `bake_ao_to_texture(obj, size, samples, distance)` を
  新設した。`bake_ao_to_vertex_colors` と同じくAO(環境遮蔽)を焼くが、
  焼き先をカラー属性ではなくテクスチャにする。UVアンラップ
  (`smart_project`)を1回行い、オブジェクトが持つマテリアルスロット
  すべてにそれぞれ専用の画像を割り当て、`bake(type="AO")` を1回
  呼ぶだけで面のマテリアル割り当てに応じて各画像へ書き分けられる
  (`assign_materials_by_region` で1枚のメッシュを複数マテリアルに
  塗り分けたガルドの本体でも、マテリアルの数だけbakeを繰り返す必要は
  ない)。焼いたAOは各マテリアルの元のBase Color値とピクセル単位で
  掛け合わせ、「色×AO」を1枚のテクスチャに合成してからBase Colorへ
  繋ぎ直す(Base Color自体は白(1,1,1)に統一し、色・陰影のすべてを
  テクスチャに持たせる。three.js側でmapがmaterial.colorに掛かる
  仕組みと対称)。`export_glb` は、UVを持つ(=このテクスチャ経路を
  通した)メッシュには従来の頂点カラーAOベイクを重ねて掛けない
  よう分岐した(二重に暗くなるのを防ぐ)。
- ガルドは本体(肌・上着・ズボン・靴・鉢巻き)だけでなく、`join()`で
  統合される装飾品(鼻・口・房紐・ベルト・背負いダル・肩ひも・なた等)
  も含めて一括でテクスチャ化した。マテリアル数は当初の想定
  (「5枚前後」)より多い20枚になったが、いずれも128×128の小さい
  画像で(単色に近い塗りがほとんどでPNG圧縮が効くため)、ガルド1体で
  .glbが約400KB→約530KBの増加にとどまった。マテリアル単位でなく
  部位単位でまとめたアトラス化は、今回は見送った(将来の最適化課題)。
- **色空間のバグとその修正**: 実装中に重大な回帰を発見した。
  `make_material`のBase Colorはリニア値だが、Cyclesが焼いたAOの
  ピクセルバッファもリニア値であり、そのまま(リニア値どうし)
  掛け合わせてglTFへ書き出すと、glTFローダー側の sRGB→リニア
  デコードが二重にかかり、暗部が破綻して全身が単色の赤茶色に
  つぶれる(ACESトーンマッピングを掛けると特に顕著。実機playtestの
  シェーダーエラーではなく、`npm run preview-engine`のスクリーン
  ショットとピクセル値の直接比較で発覚した)。`common.py`に
  `linear_to_srgb`(`srgb_to_linear`の逆関数)を新設し、Base Color
  読み出し時にsRGBへ戻してから掛け合わせることで解消した
  (新旧比較スクリーンショットで、テクスチャ化後の方がより鮮やかに
  見えることを確認)。
- 目(白目・瞳。`eye-blink-liveliness.md`でjoin()から外し頭骨へ
  剛体で親化済み)は今回のテクスチャ化の対象外で、既存の頂点カラー
  のまま。ただし瞳(`pupil`)は眉(`brow`)と同じマテリアル
  (`garudo_eye`)を共有しているため、マテリアル側がテクスチャ化
  されると瞳もそのテクスチャを参照する状態になる。瞳自体はUV
  アンラップされていないため実際には(0,0)付近を参照するが、
  その付近は未使用領域で黒に近く、瞳の色(ほぼ黒)とほぼ一致するため
  実害は無いことをズーム画像で確認した。ただし本質的には偶然の
  一致であり、瞳を独立マテリアルに切り出す方が正しい
  (将来のテクスチャ展開時に、目の造形を見直す回でまとめて対応する)。
- **2・3. テクスチャの規模・ポリゴン予算表**: ガルドの三角形数
  (7,400)は新予算(4,000〜7,500)の上限にほぼ収まっており、本書が
  想定したとおり作り直しは不要だった。表そのものは今後の展開の
  基準として本書に残る。
- **5. 描画側への影響**: 実装済み。`toToonMaterial`は変更不要
  だった(既にmapを引き継ぐ実装だったため)。`assets.ts`に、
  非スキンメッシュ向けの輪郭線処理(`addRigidOutlineMesh`。
  `eye-blink-liveliness.md`由来)がテクスチャ付きマテリアルとも
  問題なく共存することを確認した。
- 展開順2(全67種+建物+地形タイルへの拡大)、受け入れ基準3
  (モバイル実機のfps・テクスチャメモリ計測)は今回のスコープ外。
  次のパイロット候補はガルドと同じ`build_skinned`構成を持つ
  シンプルな種族(ぷるん)から。
