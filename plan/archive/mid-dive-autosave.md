# ダイブ中オートセーブ(クラッシュ対策)

> **実装済み。** `src/core/rng.ts`(`getState`/`fromState`)・`src/game.ts`
> (`RunSnapshot` 型・`toSnapshot()`・コンストラクタの `resume` オプション)・
> `src/save.ts`(`saveRunSnapshot`/`loadRunSnapshot`/`clearRunSnapshot`)・
> `src/main.ts`(起動時の復帰・ターンごとの保存・正規終了時のクリア)。
> テストは `tests/mid-dive-autosave.test.ts`。
>
> 実装時の追加・簡略化:
> - 仕様書の `RunSnapshot` には無いが、`actorIdCounter`・`itemUidCounter`・
>   `barrelIdCounter` を追加した。無いと復帰後に新規発行するidが
>   既存のアクター・アイテムと衝突しうるため。
> - `previousGimmick`・`monsterHouseWarned`・`firstStrikeAvailable` の
>   ような演出寄りの内部状態はスナップショットに含めていない(復帰時に
>   初期値へ戻っても、フロアギミックの連続回避が1回だけ緩む・
>   モンスターハウスの気配メッセージが再度出る・双樽鉤の初撃必殺が
>   復活する、程度の軽微な影響に留まるため)。
> - JSON化を経由すると `player`/`allies` と `floor.actors` 内の対応する
>   要素が別オブジェクトになってしまう問題があり、復帰時に id を頼りに
>   参照を統一し直す処理を追加した(仕様書には無い実装上の注意点)。
> - セーブ枠(`design/ui-flow.md`)が未実装のため、「セーブ枠に紐づく
>   キー」ではなく単一キー(`garudo-dungeon/v1/run-snapshot`)で近似した。
> - タイトル画面(`design/ui-flow.md`)も未実装のため、「つづきから」の
>   選択は無く、起動時に有効なスナップショットがあれば無条件に復帰する。

現状、自動保存されているのは拠点の状態(倉庫・所持金など、`src/save.ts`
の `SaveData`)だけで、**ダイブの途中経過(今どの階にいるか、HP、
持ち物、仲間の状態)は保存されていない**。`design/playtime-estimate.md`
の通り1ダイブが長いと1〜2時間規模になりうる現在の設計では、ブラウザが
落ちる・タブを閉じてしまう等でダイブ全体が消えるのは影響が大きい。
これを**クラッシュ対策としてのターンごとスナップショット**で補う。

## これは何のための機能か(重要な線引き)

**セーブ&ロードによるやり直し(セーブスカム)を許可する機能ではない。**
`plan/checkpoint-select.md` の通り、めざめの階段を使わない限り、ダイブの
途中経過を確定させて安全を確保する手段は無いという緊張感がこのゲームの
核(`design/balance-philosophy.md`)。本機能はその緊張感を変えず、
**不慮の中断からの1回限りの復帰**だけを保証する。

- スナップショットは**復帰した瞬間に消費され、消える**。同じ場面を
  何度も読み込み直すことはできない(通常のプレイの延長として、
  そのまま続きのターンへ進むだけ)。
- 全滅・踏破・めざめの階段の使用など、そのダイブが正規に終わった
  時点でもスナップショットは消える。
- ブラウザを閉じる操作そのものを技術的に「事故か、意図的な中断か」で
  判別することはできない。そのため**理屈のうえでは意図的な中断からの
  復帰も可能になってしまう**が、これは許容する。1回読み込んだ時点で
  スナップショットは消費され、以後は普通に進行するだけなので、
  連続してセーブスカムを繰り返すような使い方は成立しない
  (毎回タブを閉じては開き直す、という手間に見合わない)。

## 保存のタイミング

- **プレイヤーの入力で1ターンが解決するたび**(README記載の
  「core が1ターン分を即座に解決し `GameEvent[]` を返す」直後)に、
  現在の `Game` の状態をまるごとスナップショットとして書き出す。
- 頻度は高いが、フロアの規模・持ち物の量を考えれば `JSON.stringify` +
  `localStorage` への書き込みは軽量(README記載の通りこのゲームは
  もともと `localStorage` だけで完結する設計であり、同じ枠組みに乗る)。

## 保存する内容

```ts
export interface RunSnapshot {
  seed: number;
  rngState: number;         // Rng.state をそのまま保存し、続きの乱数列を再現する
  maxDepth: number;
  depth: number;
  floor: FloorState;        // タイル・アクター・アイテム・タル・罠を含む現在階の全状態
  player: PlayerState;
  allies: Actor[];
  status: RunStatus;
  // 表示専用の演出中フラグ等は含めない(ターン解決直後、演出が始まる前の状態を保存する)
}
```

`Rng`(`src/core/rng.ts`)は内部状態が単一の数値(`state`)なので、
乱数列を保存・復元するコストは低い。フロア生成をシードから再現するの
ではなく、**すでに解決済みの状態をそのまま書き出す**ため、復帰時に
再生成や再計算は発生しない。

## 保存先

拠点の `SaveData`(セーブ枠ごと、`design/ui-flow.md` の3枠)とは別の
キーに、**セーブ枠に紐づく形で1つだけ**持つ。

```
garudo-dungeon/v1/slot{n}/run-snapshot
```

## 復帰の流れ

1. タイトル画面(`design/ui-flow.md`)で「つづきから」を選んだとき、
   選んだセーブ枠に `run-snapshot` が残っていれば、拠点画面を経由せず
   **そのままダイブの続きから**再開する。
2. 再開時、短いメッセージ(「前回の続きから再開します」)を出し、
   これが通常の拠点スタートとは違う特別な状態であることを示す
   (`design/flavor-details.md` の演出方針に沿う)。
3. 復帰した瞬間に `run-snapshot` を削除する(前述の「1回限り」の担保)。

## 未決事項

  復帰位置(直前のターン解決結果に丸めて復帰する、という単純な仕様で
  十分か)
- 複数タブで同じセーブ枠を開いた場合の競合(最後に書き込んだ方が勝つ、
  という単純な `localStorage` の性質のまま許容するか)
- スナップショットのデータ量が大きくなった場合の書き込み頻度の調整
  (実装後、実際の階層規模で計測してから判断する)
