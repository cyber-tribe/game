> **実装済み。** 計画書どおり、コアロジック(`src/core`・`src/game.ts`)
> には一切手を入れず、`Input`クラスに`press(code)`/`release(code)`を
> 公開メソッドとして追加しただけで、`src/ui/touch-controls.ts`(新規)
> `TouchControls`が仮想パッド・ボタンをキーボードと同じキーコード
> ("ArrowUp"・"Space"等)で表現する形にした。既存の`keydown`/`keyup`
> ハンドラも内部的にこの2メソッドを呼ぶよう軽くリファクタし、キーボードと
> タッチが完全に同じ経路を通るようにした。
>
> **`plan/attack-button.md`は本セッション時点で未実装**(コア移動・攻撃
> 仕様の大規模な書き換えのため、別途のリスク判断で見送っている)なので、
> 計画書が前提としていた専用の攻撃ボタンは設けていない。パッドでの移動が
> 現行どおり敵への接触攻撃を兼ねる。
>
> **仮想パッド**: 未決事項だった方式は「ドラッグ式(指を離した位置から
> 相対で方向を出す、ジョイスティック風)」を採用した(固定8方向ボタン式
> より実機でのタップ精度に寛容だと判断)。中央のデッドゾーン内で
> ドラッグせずに離す(=軽くタップする)と、計画書が軸とした案どおり
> 「その場で待つ」(1回だけ)を発行する。連打防止のため、1回のタッチに
> つき最大1回のwaitに限定した。
>
> **ジェスチャー**: 視点回転(1本指ドラッグ、64px移動ごとに90度スナップ)
> ・ズーム(2本指ピンチ、48pxの縮尺変化ごとに1段)は、いずれも`#scene`
> canvas上の`pointerdown`/`pointermove`を`pointerType === "touch"`に
> 限定して監視し、`KeyQ`/`KeyE`/`Equal`/`Minus`の1回きりのタップとして
> 発行する(Rendererに直接触れず、既存のアクションキー経路を再利用)。
>
> **既存メニューとの整合(計画書の範囲外だが実装した挙動)**: 計画書は
> 「個々のメニュー画面のタッチ対応は範囲外、タップ=カーソルを合わせて
> 確定、という規則だけを定める」としていたが、実装時に**一度きりの
> タップ操作(ボタン・≡メニューの項目)は、まず既存の`Input.onKey`
> (もちもの・めざめの階段の確認モーダル等が使う横取り口)へ渡し、
> どのメニュー・モーダルも開いていないときだけ`press`/`release`へ
> フォールバックする**という配線にした。これにより、たとえば
> `plan/archive/stairs-confirm-modal.md`の確認モーダルが開いている
> 状態でタッチの「決定」ボタンをタップしても、キーボードのSpaceと
> 全く同じにモーダル側が処理する(モーダルを無視して素通りしない)。
> ブラウザのタッチエミュレーションで、モーダル表示中の「決定」タップが
> 正しくモーダルの選択(既定の「やめる」)を確定して閉じることを確認済み。
> 一方、パッドでの移動(継続的な押しっぱなし状態)は`onKey`を経由させず
> 直接`held`へ反映する(キーボードの矢印キーがメニュー表示中は`onKey`に
> 横取りされて`held`に入らないのと構造は異なるが、`step()`側の
> 「いずれかのメニューが開いていれば移動を処理しない」既存ガードが
> そのまま効くため、実害は無い)。
>
> **低頻度操作(T/C/R/P/H)**は計画書どおり「≡」ボタン1つにまとめ、
> タップで開く小さな一覧から選ぶ形にした。F(タルの持ち上げ/下ろし)・
> G(投げる)は常時表示にした(計画書は「タルが近くにある/抱えている
> ときだけ表示」を提案していたが、対象樽の有無判定を追加するコストに
> 見合わないと判断し、キーボードのF/Gと同じく常時押せる形に簡略化した。
> 未決事項として申し送る)。
>
> **表示条件**: `@media (pointer: coarse)`でタッチ可能な端末にだけ
> `#touch`を表示する(CSSのみで判定、JS側の端末判定は行わない)。
> キーボードと共存できる端末(タブレット等)でも、ポインタがcoarseで
> あれば両方使える(計画書の「キーボードとの共存」方針どおり、
> `Input`側は入力元を区別しない)。
>
> **対象外のまま残した未決事項**: Shift(向きだけ変える)の代替
> ジェスチャーは実装しなかった(タッチでは向き変更の手段が無い状態。
> 実機での使用感の検証が必要という計画書の指摘どおり、今回は見送り)。
> 縦持ち対応の可否も未決のまま(横持ち前提のレイアウトのみ実装)。
> ボタンサイズ・配置の具体的な数値は実機での調整前提の暫定値。
>
> UI層(`src/ui/*.ts`)は既存の`StanceMenu`等と同様vitestの対象外
> (DOM前提)のため専用のunitテストは追加せず、Playwrightの
> タッチエミュレーション(`hasTouch`・CDPの`Input.dispatchTouchEvent`)
> によるスモークテストで検証した: `pointer: coarse`下でのタッチUI表示、
> パッドのドラッグによる実際の移動、中央タップでの1回だけのwait、
> アクションボタンでのもちものメニュー開閉、≡メニュー経由のフォトモード
> 切り替え、階段確認モーダルとの相互作用、いずれもコンソールエラー無しで
> 確認済み。

# タッチ操作(スマートフォン対応)

`adr/0001-mobile-release-via-capacitor.md` が「タッチ操作向けのUI/UX
調整(仮想パッド・ボタン配置など)は別の実装単位として `plan/` 側に
仕様書を立てて扱う」としていた、その仕様書。ADRの方針(ゲームロジック・
描画コードは変更せず、配信形態が増えるだけ)を引き継ぎ、**入力の発生源を
増やすだけ**の設計にする。

## 前提: 既存の入力の形

`src/view/input.ts` の `Input` クラスは、キーボードの押下状態を
`held`(内部Set)で管理し、`direction()` `turnOnly` `hurrying`
`takeAction()` という形でゲーム側に渡している。現在のキー操作は
15種類(移動8方向 + 以下)。

| キー | 操作 | 頻度 |
|---|---|---|
| 矢印/WASD/テンキー | 8方向移動(押しっぱなしで歩き続ける。敵のいる方向へ進むと押し出す) | 常時 |
| **攻撃キー(新規、`plan/attack-button.md`)** | **向いている方向を攻撃(その場から動かない)** | **高** |
| Shift + 方向 | その場で向きだけ変える | 中 |
| Space | 拾う/階段を降りる(確定) | 高 |
| `.` / テンキー5 | 足踏み(待つ) | 高 |
| F | タルを持ち上げる/下ろす | 中 |
| G | タルを投げる | 中 |
| I | もちもの | 高 |
| T | 仲間への指示 | 低 |
| C | 樽守りの技 | 中 |
| Q / E | 視点回転(90度) | 中 |
| `+` / `-` | ズーム | 低 |
| R | 区切り/再挑戦 | 中(ダイブの節目のみ) |
| P | フォトモード | 低 |
| H | 操作説明 | 低 |

`plan/attack-button.md` により、移動キーは「移動、または敵の押し出し」に
役割が変わり、攻撃は新設の専用キーに分離された。16種類すべてを均等に
ボタン化すると画面が埋まる。**頻度で層分け**し、一部は指の自然な動き
(ジェスチャー)に置き換える。

## レイアウト方針(横持ち基本)

3Dの視野の広さを活かすため、**横持ちを基本**とする。縦持ちは「対応
しない、または横持ちを促す表示に留める」ことを提案する(詳細は
未決事項)。

```
┌─────────────────────────────────────────────┐
│                                               │
│               3Dビューポート                  │
│         (1本指ドラッグ=視点回転、             │
│          2本指ピンチ=ズーム)                   │
│                                               │
│  ○(仮想パッド)     [攻撃][I][F][G]  ((確定))  │
│  左下・8方向              右下・アクション群     │
│                                    [≡ メニュー]│
└─────────────────────────────────────────────┘
```

### 常時表示: 仮想パッド(左下)

- 移動8方向を、ドラッグして押しっぱなしにできる仮想パッドで再現する。
  離すと入力なしに戻る、既存の「押しっぱなしで歩き続ける」感覚をそのまま
  保つ。敵のいる方向へ進むと`plan/attack-button.md`の「押し出し」になる
  (キーボード版と同じ)。
- 「その場で待つ」は、パッドの中央に触れたまま(方向を出さない)を
  割り当てる案を軸にする(専用ボタンにする案との比較は未決事項)。

### 常時〜高頻度: アクションボタン群(右下)

- **攻撃(`plan/attack-button.md`の新規キーに対応)**・**確定(拾う/階段を
  降りる)**・**もちもの(I)** は常時表示。攻撃はプレイヤーが向いている
  方向に対して発動し、パッドでの移動とは独立して押せる。
- **F(タル持ち上げ/下ろす)・G(タルを投げる)** は、タルが近くにある/
  抱えている状況でのみ表示する(常に押せても意味がない場面が多いため、
  文脈に応じた出し分けで画面を節約する)。

### ジェスチャーに置き換え

- **視点回転(Q/E)** → ビューポート上の1本指ドラッグ(横方向のドラッグ量
  に応じて90度スナップで回転)。ボタンを廃止できる。
- **ズーム(+/-)** → 2本指ピンチ。同じくボタンを廃止できる。

### 低頻度操作: メニューボタン1つにまとめる(右上)

**T(仲間への指示)・C(樽守りの技)・R(区切り/再挑戦)・P(フォトモード)・
H(操作説明)** は、頻度が低い、またはダイブの節目でしか使わないため、
個別ボタンにせず「≡」1個にまとめ、タップすると一覧(リストかアイコン
グリッド)が開いてそこから選ぶ形にする。

### Shift(向きだけ変える)の扱い

キーボードの「Shift+方向」に相当する同時押しは、タッチでは自然な対応が
無い。**既に向いている方向へパッドをもう一度短くタップする**と、移動
せず向きだけ変える、という代替案を軸にするが、実際に触った感触の確認が
要るため未決事項とする。

## `Input` クラスとの接続方針

`Input.held` はキーコード文字列を要素とするSetで、`direction()` 等は
そこから読むだけなので**キーコードの中身を問わない**。タッチ由来の
入力も、同じ `held` への追加・削除という形で表現すれば、`direction()`
`turnOnly` `hurrying` の実装を一切変えずに済む。

新規に `TouchInput`(仮称)を作り、仮想パッドの押下/解放を
`"TouchNorth"` のような仮想キーコードとして同じ `held` Set操作に
変換する、という形を軸にする(具体的なクラス分割は実装セッションの
判断に委ねる。ここで重要なのは、**コアロジック `src/core` `src/game.ts`
には一切手を入れずに済む**という設計上の保証)。

`takeAction()` が扱う一度きりの操作(確定・もちもの等)も同様に、
ボタンのタップを `pending` への push に変換するだけでよい。

## メニュー画面(もちもの・仲間への指示 等)のタッチ対応

既存のメニュー(もちもの・仲間への指示・樽守りの技)は、方向キーで
カーソルを動かし確定キーで選ぶ、キーボード前提の作りになっている。
個々のメニュー画面のタッチ対応(項目を直接タップして選べるようにする
実装)は本文書の範囲外とするが、**「項目をタップする」=「その項目に
カーソルを合わせてから確定した」のと同じ結果になる**、という一貫した
規則だけをここで定める。個別画面の実装はこの規則に沿って行う。

## キーボードとの共存

タブレット等、タッチとキーボードの両方が使える端末もありうる。
`Input`(キーボード)と `TouchInput` は独立したソースとして両方
常に有効にし、**どちらの入力が先に来てもそのまま `held` に積む**
だけでよい(排他制御は不要。同じ方向を両方から受け取っても
`direction()` の結果は変わらない)。

## この文書が扱わないこと

- Capacitorの導入・ネイティブプロジェクト生成そのもの(ADR記載の通り
  別コミット)
- ストア課金・広告SDK等の収益化機能
- 実績・セーブなどモバイル固有のプラットフォーム連携(Game Center等)
- 縦持ち対応の要否そのものの決定(未決事項に記載)
