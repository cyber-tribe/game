# 自動テストプレイによる不具合検知

`plan/bug-report.md`(廃止)・`plan/community-leaderboard.md`(廃止)は、
いずれもプレイヤー自身のGitHub操作を起点にしていたため、投稿の最後の
一歩をプレイヤーが手動で行う必要があるUX上のトレードオフを理由に廃止
した。一方、`design/server-architecture.md` が示す通り、**リポジトリへの
イベントだけで起動し、プレイヤーの操作を経由しないワークフロー**なら
この制約と無縁でいられる。ここでは、その形で**プレイヤーの代わりに
ゲームを遊び、見つけた不具合を自動でGitHub Issueに起票するエージェント**
を設計する。

## 位置づけ

| | `npm run playtest`(既存) | 本文書のエージェント(新規) |
|---|---|---|
| 目的 | 決まった導線が壊れていないかの機械的な回帰確認 | まだ知らない不具合を探す |
| 動き方 | `tools/playtest.mjs` の固定シナリオを毎回同じ順序でなぞる | ランダム/準ランダムな入力で自由に探索する |
| 実行タイミング | `ci.yml`、PRのたびに毎回 | 定期実行(夜間バッチ想定)。プレイヤーからの報告を代替する |
| 失敗時の扱い | CIを赤くする(その場でわかる) | GitHub Issueを起票する(後から人が見る) |

既存の `npm run playtest` を置き換えるものではなく、両方を維持する。
プレイヤーからの手動報告経路が無くなった今、**このエージェントが唯一の
自動的な不具合発見手段**になる(人が手動でIssueを立てる経路自体は元々
GitHubの標準機能としてどのプロジェクトにもあり、これは変わらない)。

## 探索方法

- `tools/playtest.mjs` と同じ土台(Playwright ヘッドレス、SwiftShader
  でのWebGL起動)を使い、新規スクリプト `tools/auto-tester.mjs` を作る。
- 固定シナリオではなく、**重み付けランダムなキー入力**を一定ターン数
  繰り返す「セッション」を、1回の実行で複数独立に行う。
- 各セッションの開始時に使う**乱数シード**(`src/core/rng.ts` の
  `Rng.state`)と、**入力選択に使う乱数シード**の両方を記録する。両方が
  揃って初めて、見つけた不具合を後から人が再現できる。

### 入力の重み付け(1ターンあたりの行動選択)

| 行動 | 重み |
|---|---|
| 移動(4方向のいずれかを1〜3ターン分押し続ける。モンスターに隣接すれば体当たりで攻撃になる) | 60% |
| その場で待つ(`Period` キー。満腹度の減少やモンスターの行動を進める) | 15% |
| 持ち物メニューを開いて操作する(`KeyI` → ランダムな項目を選ぶ → 閉じる) | 10% |
| 視点回転(`KeyE`) | 5% |
| 仲間への指示(`plan/companion-orders.md`。仲間がいる場合のみ) | 10% |

具体的な配分は実装時のチューニング対象とする(下記未決事項)。

### 階層の進め方

自然に階段を見つけるまで歩かせるだけでは、限られたターン予算の中で
訪れる階層が偏ってしまう。そこで、**1セッションの中でターン予算の
7割を消化した時点で、まだその階にいれば `debugDescend`(既存のデバッグ
用フック、`tools/playtest.mjs` も使用)で強制的に次の階へ進める**。これは
「本物の階段探しの動き」をテストする目的ではなく、「1回の実行でより
多くの階層のコンテンツに触れる」ための効率化であり、両立させる。

### 実行規模

- 1回の実行につき **8セッション**、1セッションあたり**最大200ターン、
  または3分の壁時計時間(先に達した方)**で打ち切る。
- 8セッション合計でも実行時間は30分程度に収まる想定で、GitHub Actions
  の無料枠内で毎日実行しても問題にならない規模にとどめる。
- 実行頻度は**毎日1回(既定のcronのまま)**とし、実装セッションの活動量
  に応じて動的に変える仕組みは今は作らない(`workflow_dispatch` による
  手動実行が、大きな変更の直後にすぐ確認したい場合の代替になる)。

## 異常の検知

`tools/playtest.mjs` が既に持っている検知(`pageerror` / コンソール
`error` / 4xx・5xx応答 / `requestfailed`)をそのまま使う。加えて、

- **応答なし(ハング)検知**: 一定時間(例: 10秒)ごとにHUD状態を
  `page.evaluate` で読みに行き、タイムアウトしたら「応答なし」として
  異常扱いにする。
- **進行不能(ソフトロック)の疑い検知**: **連続20ターンの間、かつその
  間に上下左右のうち3方向以上を実際に試みたにもかかわらず**、HUD状態
  (階・座標・HP等)が一切変化しない場合、低確度の異常として記録する。
  「3方向以上試みた」を条件に含めるのは、単に壁際で同じ方向を押し続けて
  いるだけの状態(プレイヤーの意図的な待機と区別がつかない)を誤検知
  しないため。誤検知が起きやすい項目であることに変わりはないため、
  後述の `low-confidence` ラベルで区別する。

## 収集する情報

`RunSnapshot`(`src/game.ts`、既存)をそのまま使う。プレイヤー向け機能
だった `plan/bug-report.md` の `BugReport` 型と考え方は同じだが、今回は
**URLに載せる必要が無い**(サーバー側からAPIへ直接JSONを送るだけなので、
`?body=` のURL長制限もクリップボード経由の貼り付けも不要になる)。

| 項目 | 内容 |
|---|---|
| 発生状況 | エラーメッセージ、スタックトレース、`screen`(title/town/dungeon) |
| ダイブの状態一式 | `RunSnapshot` を使う(サイズ対策として `floor.tiles` は除いたトリミング版。URL制限は無いが、Issue本文の長さには上限があるため、この方針は引き継ぐ) |
| 再現用の乱数シード | 上記の2種類のシード |
| 直近の出来事 | `GameEvent` 列、直近数十件 |
| スクリーンショット | PNG。**Issue本文へは直接埋め込めない**(GitHub REST APIには、Web UIのドラッグ&ドロップが使う画像アップロード機能に相当する公開エンドポイントが無いため)。`actions/upload-artifact` でワークフローの実行成果物として保存し、Issue本文にはその実行(Actions run)へのリンクを貼る。 |
| ゲームのバージョン | ビルド時に埋め込むコミットハッシュ |

## Issue作成(サーバー側で完結)

このエージェントはGitHub Actions上で動くため、`design/server-
architecture.md` 原則3の通り、その実行のたびに自動発行される
`GITHUB_TOKEN`(`issues: write`)を使い、`actions/github-script` から
直接GitHub APIを呼んでIssueを作成する。プレイヤーの操作もブラウザの
新規Issue画面も経由しない(この点が `plan/bug-report.md` との根本的な
違いで、廃止の原因になったUX上の制約をそもそも持たない)。

## 重複投稿対策

エージェントは定期的に(想定: 毎晩)動くため、**直っていない不具合を
毎回別のIssueとして起票し続けてしまう**リスクが最大の懸念になる。対策を
何段階かに分けて設計する。

### 1. 実行内(1回のバッチ)ではまず1件にまとめる

1回の実行で複数セッションを回すため、同じ不具合を同じ実行内で何度も
踏むことがある。GitHub APIを呼ぶ前に、実行内で見つけた異常をすべて
フィンガープリント(下記)ごとにメモリ上でグルーピングし、**1回の実行
につき同じフィンガープリントからは最大1回しかAPIを呼ばない**。

### 2. フィンガープリントの作り方

次の3つを連結し、SHA-256でハッシュ化したものを使う。

- **発生場所の大まかな区分**: `screen`(title/town/dungeon)。ダンジョン
  なら地方名までとし、**階数は含めない**(同じ不具合が別の階で起きても
  本質的には同じ不具合であることが多い)。
- **正規化したエラーメッセージ**: メッセージ中の可変値を正規表現で
  置き換え、実行のたびに変わる値でフィンガープリントがぶれないようにする。

  ```js
  function normalize(message) {
    return message
      .replace(/\b[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\b/gi, "<UUID>")
      .replace(/\b0x[0-9a-f]+\b/gi, "<HEX>")
      .replace(/\b\d+(\.\d+)?\b/g, "<N>");
  }
  ```

  UUID・16進数のような形が特徴的なものを先に潰してから、最後に残った
  素朴な数値をまとめて `<N>` に置き換える(先に数値だけ潰すと、UUID・
  16進数の中の数字がバラバラに壊れて判定に使えなくなるため、順序が
  重要)。
- **スタックトレース最上位フレームの関数名・ファイル名**(**行番号は
  含めない**)。実装セッションはこのゲームを毎日のように更新している
  ため、行番号までフィンガープリントに含めると、直っていない不具合が
  無関係な変更のたびに「新しい不具合」として再起票されてしまう。

ハッシュは `<!-- auto-tester:fingerprint:sha256:... -->` という隠し
コメント行としてIssue本文に埋め込み、検索対象にする。

### 3. 起票前に既存Issueを検索する

`auto-report` ラベル(このエージェント専用の新しいラベル)を持つIssueを
open・closed問わず検索し、本文に同じフィンガープリント文字列を含む
ものが無いか確認する。

- **openで見つかった場合**: 新規Issueは作らない。ただし完全に無視すると
  「まだ直っていないか」が追いにくくなるため、**最後にこのフィンガー
  プリントへコメントしてから24時間以上経っている場合に限り**「またN回
  再現しました」と1件だけ追記コメントする(それ未満ならコメントも
  しない。1日に何度もコメントされる状態を避ける)。
- **closedで見つかった場合**: `state_reason` を見て分岐する。
  - `completed`(直したとして閉じられていた)→ **再発(リグレッション)**
    として扱い、Issueを再オープンし「直したはずが再発しました」と
    コメントする。
  - `not_planned`(対応しないと判断されて閉じられていた)→ **起票しない**。
    実行ログには残すが、Issueとしては作らない(人間が下した判断を
    エージェントが勝手に覆さない)。

### 4. 1回の実行あたりの新規Issue数に上限を設ける

フィンガープリントの正規化が効かず、同じ根本原因が微妙に違う
フィンガープリントとして大量に検出されてしまう事態への保険として、
**1回の実行で新規に作成するIssueは最大5件まで**とし、それを超えた分は
実行ログに集計を残すだけでIssue化しない(サーキットブレーカー)。
8セッション×1セッション最大数件という規模感(前述「実行規模」)に対して、
5件は「明らかに異常な多発」を検知するのに十分低い一方、正常な実行でも
2〜3種類の新規不具合が同時に見つかることはありうるため、それを潰さない
程度の余裕を持たせた値としている。

### 5. 状態の持ち方

GitHub Actionsの実行自体はステートレスなので、「既に見た不具合か」の
唯一の正はリポジトリのIssue自体とする(`design/server-architecture.md`
原則4)。重複管理のための追加データベース・追加ファイルは持たない。

## ワークフロー形状

```yaml
# .github/workflows/auto-tester.yml (新規)
on:
  schedule:
    - cron: "0 18 * * *"   # 毎日 JST 3:00(UTC 18:00)。開発時間帯を避ける
  workflow_dispatch: {}     # 手動での随時実行も許可する
permissions:
  issues: write
  contents: read
jobs:
  explore:
    runs-on: ubuntu-latest
    steps:
      - checkout / npm ci / ビルド or 開発サーバー起動
      - run: node tools/auto-tester.mjs
      - uses: actions/upload-artifact@v4   # スクリーンショット等
        if: always()
        with:
          retention-days: 14
      - uses: actions/github-script@v7      # 検索・重複排除・Issue作成
        if: always()
```

`contents: write` は不要(スクリーンショットはコミットせずアーティファクト
として保存するため)。追加のシークレットも要らない
(`design/server-architecture.md` 原則3)。

## ラベル体系

- `auto-report`: このエージェントが作ったIssueであることを示す新しい
  専用ラベル(廃止済みの `bug-report` / `leaderboard-submission` とは
  無関係)。
- `needs-triage`: 起票直後に付ける。**自動でクローズしない**(廃止前の
  `plan/bug-report.md` と同じく、開発側が調査するまでオープンのまま
  にする)。
- `screen:*`: 発生画面ごとのラベル(廃止前の設計を踏襲)。
- `low-confidence`: 進行不能(ソフトロック)の疑いのような、誤検知が
  起きやすい種類の異常に付け、優先度を判断しやすくする。

## スクリーンショットの保持期間

`retention-days: 14`(前述ワークフロー)とする。不具合の技術的な裏付け
(`RunSnapshot`・スタックトレース・再現用シード)はテキストとしてIssue
本文に残り続けるため消えないが、視覚的な補助資料であるスクリーンショット
は14日あれば通常のトリアージ・調査には十分で、それ以上長く持たせて
Actionsのストレージを消費し続ける理由が無いと判断した。
