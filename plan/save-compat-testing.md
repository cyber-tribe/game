# セーブデータの後方互換チェック

`src/save.ts` の `loadSave()` は、フィールドごとにサニタイズ関数
(`sanitizeStorage` `sanitizeHut` `sanitizeCompendium` 等)を通し、壊れた
値・存在しない値は初期値へ黙って差し戻す設計になっている。さらに
`JSON.parse` 自体が失敗した場合も丸ごと `initialSave()` へフォールバック
する(「壊れた保存データで起動できなくなるほうが困るので、黙って初期値に
戻す」という既存のコメント通り)。**この設計はクラッシュしないことは
保証するが、「静かにデータの一部が消える」ことまでは防げない。**

難易度モード・鍛え方・なじみ成長・衣装・命名など、`SaveData` はこれまで
何度も拡張されてきた(`src/save.ts` を見るだけでも十数個のフィールドが
ある)。今後もフィールドのリネーム・IDセットの変更・サニタイズ関数の
ロジック変更は起き続ける。そのたびに「昔のセーブを読み込んだら、実は
一部の進行状況(図鑑・実績・倉庫の中身等)が黙って消えていた」という
不具合が、テストなしでは検知できないまま入り込みうる。

## 仕組み

新規テストファイル `tests/save-compat.test.ts` を作り、**過去の主要な
節目のセーブデータを模した固定のJSONフィクスチャ**を複数世代分保持する。
各フィクスチャに対して `loadSave()` を呼び、**「クラッシュしない」では
なく「その世代で存在していたはずのフィールドの値が保持されている」**
ところまで assert する。

```
tests/fixtures/save/
  v1-initial.json           # 最初期のフィールド構成
  v2-difficulty.json        # 難易度モード追加後
  v3-village-development.json  # 村の発展追加後
  ...
```

- 各フィクスチャは「進行が進んだ状態」(倉庫にアイテムがある、図鑑が
  一部埋まっている、実績がいくつか解放されている等)を表すものにする。
  空の初期状態だけをテストしても、フィールドが消えても気づけない。
- テストは各フィクスチャについて、`loadSave()` の結果から**その世代で
  意味を持つフィールドの値が、フィクスチャに書いた通りに残っている**
  ことを確認する(例: `v1-initial.json` を読み込んだら `storage` の
  中身・`achievements` の解放状態が消えていないか)。
- 新しく増えたフィールド(そのフィクスチャの時点では存在しなかった
  もの)は、`initialSave()` と同じ既定値になっていることを確認する
  (欠けているフィールドへの複合が正しく効いているかの確認を兼ねる)。

## 対象範囲

- **`loadSave()`(拠点のセーブデータ)を対象にする。**
- `loadRunSnapshot()`(ダイブ中オートセーブ)は対象外とする。
  `plan/mid-dive-autosave.md` の設計上、既に「壊れていれば復帰を諦めて
  `null` を返してよい」(1回限りの保証)という方針が明記されており、
  後方互換を保証する対象として扱っていない。この既存の設計判断は
  変えない。

## フィクスチャの運用

- 新しいフィクスチャを追加するタイミングは、**`SaveData` にフィールドを
  追加・変更する実装のたびに1つ**、を目安にする(すべてのコミットを
  追う必要はなく、セーブフォーマットに影響する節目だけで十分)。追加は
  実装セッションの裁量に委ねる。
- 一度追加したフィクスチャは**削除しない**(過去のセーブへの互換性を
  今後も切らない、という前提そのものを表すテストのため)。世代が増える
  ことによるテストコストの増加は許容する。

## CIへの組み込み

新しいワークフローは不要。`tests/save-compat.test.ts` は既存の
`npm test`(vitest)にただのテストファイルとして加わるだけで、
`ci.yml` の既存ジョブ(型・テスト・ビルド)がそのまま拾う。
`design/server-architecture.md` のようなサーバー機構は関係が無い、
純粋なユニットテストの話として位置づける。
