# テスト用の箱庭ダンジョン ― フロア状態を外から差し込めるテスト基盤

## 経緯

現状の自動テストは `tools/auto-tester.mjs`(実ダンジョンを乱数で
回すプレイテスト)に寄っており、**単体テスト(vitest)が存在しない**
(`npm test` はあるがテストファイルが1つも無い)。実ダンジョンは
`generateFloor` の乱数で作られるため、「この配置でこの挙動になるか」
という再現条件が組めず、あらゆる検証が困難になっている。

対策として、**フロアの状態を丸ごと外から差し込める箱庭**を用意する。
テスト専用であり、ゲーム本体からは一切アクセスできない。

## 変更内容

### 1. 置き場所と隔離

- `tests/` ディレクトリをリポジトリ直下に新設し、箱庭ビルダーと
  テスト本体をすべてここに置く(`tests/harness/` と
  `tests/*.test.ts`)。
- `src/` から `tests/` への import を**禁止**する(逆は自由)。
  ゲームの本番バンドルは `src/` 起点でビルドされるため、この
  一方向ルールだけで「ゲームからアクセス不可」が構造的に決まる。
  CIに検査を1つ足す: `src/` 内に `tests/` への import 文が
  無いことを grep で確認するステップ(`ci.yml` に追加)。
- vitest の対象に `tests/**/*.test.ts` を加える。

### 2. 箱庭ビルダー(ASCIIマップでフロアを組む)

`tests/harness/floor.ts` に `buildTestFloor` を実装する。
`FloorState`(`src/core/types.ts`)を、乱数を使わず宣言的に組み立てる:

```ts
const { floor, at } = buildTestFloor(`
  ##########
  #@...p...#
  #....#...#
  #..b.#..>#
  ##########
`, {
  legend: {
    p: { actor: "purun" },
    b: { barrel: "empty" },
  },
});
```

- 記号の既定: `#`=壁 `.`=床 `>`=階段 `@`=プレイヤー初期位置。
  それ以外の文字は `legend` で意味を与える(actor種族・持ちHP、
  地面アイテム、罠、タル、金貨、障害物など、`FloorState` の
  各配列に対応)。
- 部屋(`rooms`)は矩形の床領域から自動検出する。通路・
  いびつな形はそのまま「部屋なし床」として扱う(視界処理の
  部屋依存ロジックをテストするときだけ `rooms` を明示指定できる
  オプションを持つ)。
- `at("p")` のように、記号からタイル座標を引けるヘルパーを返す
  (アサーションで座標をハードコードしない)。
- ギミック(`gimmick`)・地方・階数などのメタ情報もオプションで
  差し込める。省略時は「いつも通りの階」。

### 3. 決定的な乱数

- `tests/harness/rng.ts` に2種類のテスト用Rngを用意する:
  1. **シード固定Rng**: 本物と同じ実装をシード指定で(疑似再現用)。
  2. **列挙Rng**: `[0.0, 0.99, ...]` と値の列を直接渡し、
     「命中判定に成功する/捕獲に失敗する」を意図どおりに踏ませる。
- ゲームロジック側は既に `Rng` を引数で受け取る作りなので
  (`generateFloor(rng, opts)` 等)、差し替えだけで済む。
  もし `Math.random` 直呼びの箇所が残っていたら、この実装の
  ついでに `Rng` 経由へ直す。

### 4. ターン実行ドライバ

`tests/harness/run.ts` に、組んだフロアで応用層
(`src/application/dungeonRun/game.ts`)を頭なし(描画なし)で回す
薄いドライバを実装する:

```ts
const g = startTestRun(floor, { satiety: 100, level: 5 });
g.step("moveEast");         // 1入力=1ターン
g.step("throwBarrel");
expect(g.state.actors).toHaveLength(0);
expect(g.log).toContain("captured:purun");
```

- 入力は既存の入力コマンド列挙をそのまま使う(新しい操作体系を
  作らない)。
- プレイヤーの初期状態(レベル・満腹度・持ち物・仲間)も
  差し込める。
- 描画(`src/view/`)・音・UIは一切読み込まない。ロジック層が
  view に依存していて読み込みが避けられない箇所が見つかったら、
  それ自体を依存の欠陥として切り離す(このテスト基盤の副次的な
  効能。ヘッドレスで回らないロジックはテストできないロジック)。

### 5. 最初に書くテスト(基盤の実証)

基盤PRに、少なくとも以下の3本のテストを同梱して「あらゆるテストに
対応可能」の土台を実証する:

1. **移動と衝突**: 壁に向かって歩いてもターンを消費せず座標が
   変わらない/床なら1マス進む。
2. **戦闘の決定性**: 列挙Rngで命中と乱数幅を固定し、隣接攻撃の
   ダメージが期待値どおりになる。
3. **捕獲**: HPを削ったモンスターに空タルを当て、列挙Rngで
   捕獲成功を踏ませ、仲間リストに入る。

以後、バグ報告(GitHub issue)には可能な限り「箱庭での再現
テスト」を添えて修正する運用にする(修正PRの受け入れ基準に
再現テストの同梱を推奨として書く)。

## 受け入れ基準

1. `npm test` で箱庭を使ったテストが動き、上記3本が緑になる。
2. テストは `generateFloor` の乱数に一切依存しない
   (ASCIIマップと差し込みRngだけで完結する)。
3. 本番バンドル(`npm run build` の成果物)に `tests/` 由来の
   コードが含まれない。`src/` から `tests/` への import が
   CIで検出されたら失敗する。
4. ASCIIマップ・legend・ドライバの使い方が
   `tests/harness/README.md` に実例つきで書かれている
   (以後のテストを書く実装セッションが迷わない粒度)。

## 対象外

- 描画・シェーダーのテスト(`plan/models/engine-preview-snapshots.md`
  のスナップショットが受け持つ)
- 村・拠点のシーンのテスト基盤(まずダンジョンだけ。村は
  必要になったら同じ方式で広げる)
- 既存 `tools/auto-tester.mjs` の置き換え(乱数プレイテストは
  別役割としてそのまま残す)

## 未決事項

  有力。最初の3本には不要なので実装時に決める)
- 仲間AI・ボスAIの行動テストをどこまで箱庭で書くか(基盤が
