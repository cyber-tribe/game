> **実装済み。** `tools/audio/`(新規)に計画書どおりの構成で実装した:
> `wav.ts`(PCM16モノラル`.wav`の書き出し、外部依存なし)・`synth.ts`
> (木琴/鈴・太鼓・笛・弦=Karplus-Strong法の4種の合成関数、シード付き
> 疑似乱数`mulberry32`)・`compose.ts`(全曲共通のペンタトニック音階・
> テンポ92BPM・4小節分のコード進行の骨格、地方ごとのシード+楽器重みから
> ループ用BGMを生成する`composeTrack`、単発SFX用の`composeSfx`)・
> `build.ts`(全アセットを生成して`public/audio/`へ書き出すエントリ
> ポイント、`npm run audio`で実行)。
>
> **実行方式**: `tools/models/*.py`とは異なり、Python/Blenderではなく
> Node 22の組み込みTypeScript実行(型剥がし)をそのまま使う設計にした
> (計画書は言語を指定していなかったが、追加のランタイム・依存を
> 増やさずに済む)。ただしNodeの素のESMローダーはバンドラ方式の拡張子
> 省略importを解決できないため、`tools/audio/`内の相互import**だけ**
> 明示的に`.ts`拡張子を付けている(`src/`側の既存の書き方とは違う、
> このディレクトリ限定のローカルルール)。`tsconfig.json`の`include`に
> `tools/audio`を追加し、`allowImportingTsExtensions`を有効にして
> `tsc --noEmit`の対象にも含めた(型の検証自体は通常どおり効く)。
>
> **地方ごとの楽器重み**は`design/regions.md`の8地方の雰囲気に沿って
> 割り当てた(第一地方=木琴主体で軽く、第二地方=笛主体で霧の中、
> 第三地方=弦主体でまどろみ、第四地方=太鼓主体で乾いた回廊、
> 第五地方=笛+弦でゆったり悲しく、第六地方=木琴+太鼓で尾根の反響、
> 第七地方=木琴+太鼓で祭り囃子寄り、第八地方=4種均等)。ボス戦は
> 太鼓を厚めにして緊張感を出し、真の目覚めは弦+笛のみで太鼓をほぼ
> 鳴らさない(テンポそのものは計画書どおり全曲共通のまま変えていない)。
>
> **ファイル形式**: 計画書が実装メモで指摘していたとおり、実行環境に
> `ffmpeg`/`sox`が無いため`.ogg`ではなく`.wav`で書き出す方針を踏襲した。
> `src/audio/player.ts`の`bgmUrl`/`sfxUrl`の拡張子を`.ogg`→`.wav`に
> 変更しただけで、再生エンジン側(`decodeAudioData`)は無変更で動作した。
> `public/audio/`配下の旧プレースホルダー(0バイトの`.ogg`)は削除し、
> 生成済みの`.wav`(BGM: 村・地方1〜8・ボス・真の目覚めの11本、各
> 4小節≈10.4秒のループ、22.05kHz/モノラル/約450KB、リポジトリ合計
> 約5MB。SFX: 捕獲・レベルアップ・満腹度警告・チェックポイント・
> 爆発・ボス予兆の6本、いずれも1秒未満)をコミットした。
>
> テストは`tests/audio-synthesis.test.ts`(WAVヘッダの正しさ・PCM16への
> クランプ、各楽器合成関数が有限な値の配列を返すこと、`mixIn`の加算・
> 範囲外の扱い、`normalize`のクリップ防止、`composeTrack`のシード
> 決定性・地方ごとの違い・ピーク制限)で検証。ブラウザでも、生成した
> 全BGM・一部SFXの`.wav`が実際に`AudioContext.decodeAudioData`で
> エラー無くデコードでき、想定どおりの再生時間になることを確認済み
> (プレースホルダー時代は0バイトのため常にデコード失敗していたのが、
> 今回で実際に鳴る状態になった)。

# 楽曲・効果音を「自作」する方法(手続き的な音声合成)

`design/audio-direction.md`・`plan/archive/audio-playback.md` がどちらも
未決事項として残していた「実際の楽曲・効果音をどう作るか」を決める。
README の「3Dモデルはすべて自作(Blenderをスクリプトで動かす)」という
方針と同じ考え方を音にも当てはめ、**録音・既製サンプルに頼らず、
コードで音を合成して書き出す**方式にする。人間の作曲家・演奏者を
必要としない、この開発体制に合った選び方でもある。

## 位置づけ

`tools/models/`(Pythonスクリプト → `.glb`)と対になる、`tools/audio/`
(スクリプト → 音声ファイル)を新設する。**スクリプトと生成済みの音声
ファイルの両方をコミットする**という運用も、3Dモデルとまったく同じに
する。

```
tools/models/*.py  → public/models/*.glb   (既存)
tools/audio/*.ts    → public/audio/*.wav    (本文書)
```

## 音声合成の技法(楽器ごと)

`design/audio-direction.md` が指定する編成(木琴・太鼓・笛・弦)を、
それぞれ単純な信号処理で近似する。いずれも枯れた手法で、外部ライブラリ
無しに実装できる。

| 楽器 | 合成方法 |
|---|---|
| 木琴・鈴 | 正弦波+わずかな倍音、鋭いアタック・指数的な減衰エンベロープ(バチで叩く質感) |
| 太鼓 | フィルタしたノイズ+低い正弦波の「ドン」、短いエンベロープ |
| 笛 | 正弦波主体、緩やかなアタックとわずかなビブラート(息の揺れ) |
| 弦(琴に近い響き) | **Karplus-Strong法**(弦をはじく物理モデル。実装が単純で、はじいた弦特有の減衰音に強い) |

## 作曲の仕組み: ダンジョン生成と同じ「手続き的だが検証された」考え方

人間の作曲家がいないため、**旋律・リズムも手続き的に生成する**。
`src/core/rng.ts` の考え方(シード付き乱数で、検証を通った結果だけを
採用する)を音楽にもそのまま当てはめる。

- **音階は五音音階(ペンタトニック)に固定する。** 民謡的な響きを保ち、
  不協和な組み合わせが生まれる余地そのものを無くす(「検証」に頼らず
  設計で問題を起きなくする、ダンジョン生成のフラッドフィル検証とは
  少し違う安全策だが、狙いは同じ)。
- **テンポ・コード進行(和音の基礎になる音の骨格)は全曲共通の定数と
  して固定する。** `design/audio-direction.md` の「テンポやコード進行の
  骨格は共通にし、『同じ世界の続き』であることは崩さない」をそのまま
  満たす。
- **地方ごとに違うシード値**で旋律・リズムパターンを生成し、地方らしさは
  「どの楽器をどれだけ使うか」(木琴多め/太鼓多め 等、`design/regions.md`
  の雰囲気に対応させる)の重み付けで描き分ける。
- 村のテーマ・ボス戦テーマも同じ生成基盤の別パラメータとして作る
  (新しい仕組みを増やさない)。

## ファイル形式: `.wav` にする

`plan/archive/audio-playback.md` は `.ogg`(Vorbis)を前提にしていたが、
実装時点で `ffmpeg`/`sox` 等のエンコードツールが環境に無く、無音の
プレースホルダーで代替した経緯がある(同文書の実装メモ参照)。

**本文書では方針を変え、圧縮しない `.wav` で書き出す。** 生成した
PCMサンプル列を直接 `.wav` ヘッダ付きで書き出すだけなので、外部の
エンコードツール・追加の npm 依存を一切必要としない(README の
「外部から持ってきた素材は一つも使っていない」という姿勢に、依存関係を
増やさないという面でも合う)。ファイルサイズは、モノラル・短いループ・
控えめなサンプリングレート(目安22.05kHz)に抑えることで許容範囲に
収める。将来、環境にエンコードツールが使えるようになった場合は
`.ogg` への再圧縮を検討する余地を残すが、本文書の対象外とする。

`src/audio/player.ts`(`plan/archive/audio-playback.md` で実装済み)は
`fetch`→`decodeAudioData`で読んでいるだけなので、`.wav`に変えても
**再生エンジン側の変更は不要**(`decodeAudioData`はWAVもデコードできる)。
`public/audio/` 配下のファイル名の拡張子と、実際に置くファイルだけを
差し替えればよい。

## 効果音

BGMと同じ合成基盤を流用する。1回きりの短い音(捕獲・レベルアップ・
満腹度警告・チェックポイント・爆発・ボス予兆)は、いずれも単発の
エンベロープ付き音源(木琴/太鼓寄りの合成)で足りる。専用の仕組みは
新設しない。

## 対象外

- `.ogg` への再圧縮(将来、環境が整った場合の検討事項として残す)
- ボイス(掛け声等、`design/audio-direction.md` の未決事項のまま)
- 生成した楽曲の主観的な出来映えの調整(自動生成である以上、聴感上の
  調整が必要になった場合はパラメータ(音階・テンポ・重み付け)側で
  対応する)

## 未決事項

- 五音音階の具体的な音高、テンポ・コード進行の共通骨格の具体値
- 地方ごとの楽器重み付けの具体的な割り当て
- サンプリングレート・ループ長の具体値(ファイルサイズの実測を見て調整)
- 既存のプレースホルダー無音`.wav`/`.ogg`をいつ本物の生成音声に差し替えるか
