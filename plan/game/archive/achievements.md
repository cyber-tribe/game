# 実績・称号

> **実装済み。** `src/entities/achievements.ts`(新規。実績カタログ
> `AchievementDef`/`ACHIEVEMENTS`)・`src/save.ts`(`SaveData.achievements`
> ・`equippedTitle`、`unlockAchievement`、`checkAchievements`、
> `setEquippedTitle`、壊れたセーブデータのサニタイズ)・`src/main.ts`
> (拠点からの出発時に`checkAchievements`を呼ぶ配線、称号の着脱を
> `TownScreen`から受け取る配線)・`src/ui/town.ts`(拠点に「実績帳」
> カラムを追加。未達成の実績も条件を伏せずに表示し、称号を持つ達成済みの
> 実績はEnterで着脱できる。着脱中の称号は画面上部に「『称号』ガルド」と
> 表示する)。テストは `tests/achievements.test.ts`(14件)。
>
> 実装にあたって次の判断をした。
>
> - **収録した実績は、既に実装済みの機能だけを条件にした9件に絞った。**
>   本文の実績例には依頼板(`plan/quest-board.md`)・地方ボス
>   (`plan/region-bosses.md`)・仲間の成熟(`plan/companion-evolution.md`)
>   ・絆(`design/village-life.md`)を条件にするものが多いが、いずれも
>   まだ実装されていない機能のため、それらに依存する実績は収録していない。
>   本文が明記する「網羅的な一覧は実装時に広げる」方針どおり、対応する
>   機能の実装時に`ACHIEVEMENTS`へ追加する。
> - **「挑戦」カテゴリ(縛りプレイ的な実績)は今回見送った。** 本文の
>   未決事項が「実装コストを見て初弾に含めるか判断する」としていたとおり、
>   ダイブ中の使用武器・使用アイテムを記録する専用の仕組みが追加で必要に
>   なるため、今回のスコープからは外した。
> - **判定は専用の監視処理を新設せず、`checkAchievements`が既存のセーブ
>   フィールド(討伐・捕獲累計、踏破回数、最高レベル、図鑑、倉庫の装備)
>   を毎回まとめて再評価する設計にした。** 本文の「達成イベントの延長で
>   1行足すだけ」という方針を、複数箇所に判定ロジックを分散させるのでは
>   なく1関数に集約する形で実現している。呼び出し箇所はダイブの成果反映
>   (`recordRun`)・図鑑の「捕まえた」更新(`markSpeciesCaptured`・
>   `fuseMonsters`)・拠点からの出発時(強化・刻印の実績用に、まだ倉庫に
>   戻っていない持ち込み品も合わせて走査する)。
> - **強化(+9)・刻印(全5種)の実績は、専用の「一度でも達成した」フラグを
>   セーブデータに新設せず、倉庫(+持ち込み品)を毎回re-scanする形にした。**
>   `unlockAchievement`が一度記録した実績を取り消さない(冪等)ため、
>   re-scan方式でも「知識・記録はロストしない」原則は成立する
>   (該当装備を売る・上書きしても、既に記録した実績は残る)。
> - **かがやきの夢のかけら出現率アップの実利報酬は、`plan/monster-compendium.md`
>   側の`isCompendiumComplete`で既に実装済みのため、実績側では二重実装せず
>   記録・称号(「図鑑の達人」)としてのみ扱う。** 依頼板の受注数+1といった
>   他の実利報酬例も、対応機能が未実装のため見送った。
> - **称号は9件中3件(図鑑コンプリート・五印皆伝・はじめての踏破)にだけ
>   紐づけた。** 残りは記録専用の実績とし、本文の「実績の一部には称号が
>   紐づく」という書き方に合わせた。

これまで積み上げてきた達成要素(図鑑・依頼・絆・地方踏破・ボス撃破など)を
横断的に振り返れる**実績帳**を用意する。個々の機能が持つ「知識はロスト
しない」原則(`design/balance-philosophy.md`)の集大成として、達成した
ことそのものを記録・可視化する場を作る。

## 位置づけ

- 実績はすべて**記録側**の要素であり、`design/balance-philosophy.md` の
  「知識・記録は全滅してもロストしない」原則にそのまま従う。
- 報酬は基本的に**称号(二つ名)という飾り**に留め、数値的な強さには
  直結させない。ごく一部だけ、拠点の利便性に効く小さな報酬を混ぜる
  (詳細は下記)。実績集めが装備・強化のパワーバジェットの抜け道に
  ならないようにする。

## カテゴリと実績例

網羅的な一覧は実装時に広げるものとし、ここでは各カテゴリの性質が
分かる代表例を挙げる。

| カテゴリ | 実績例 | 出典 |
|---|---|---|
| 討伐 | 「ホネヅカのぬしを倒す」「全地方のボスを倒す」 | `plan/region-bosses.md` |
| 収集 | 「図鑑を半分埋める」「図鑑を全部埋める」「かがやきの夢のかけらを見る」 | `plan/monster-compendium.md` |
| 探索 | 「全地方のめざめの階段を知る」「夜ごとの夢で50階に到達する」 | `plan/checkpoint-select.md` `plan/multiple-dungeons.md` |
| 依頼 | 「依頼を10件達成する」「護送依頼をすべて成功させる」 | `plan/quest-board.md` |
| 絆 | 「全NPCと一定以上の絆を築く」 | `design/village-life.md` |
| 育成 | 「仲間を成熟させる」「装備を+9にする」「全種類の印を1つずつ刻む」 | `plan/companion-evolution.md` `plan/equipment-forging.md` |
| 挑戦 | 「1本の武器種だけで表の寝穴を踏破する」「一度も道具を使わずに1地方を踏破する」 | `plan/protagonist-weapons.md` |

「挑戦」カテゴリは、縛りプレイ的な達成を公式に認知する枠にする。
攻略の幅を狭めるのではなく、**やり込んだ人が選べる自分ルール**を
ゲーム側が把握・記録してくれる、という位置づけ。

## 称号

実績の一部には称号が紐づく(例:「全地方のボスを倒す」→称号
「山の静め手」)。称号は**1つだけ選んで身につけられる**飾りで、
拠点でガルドの傍らに短い名乗りとして表示する程度の演出に留める
(セーブ選択画面やエンディングでの表示を想定)。

## ごく小さな実利報酬(例外)

以下のように、称号だけでなく小さな利便性が付くものも一部用意してよいが、
`design/balance-philosophy.md` の方針どおり**攻撃力・防御力には触れない**。

- 「依頼を10件達成する」→ 依頼板(`plan/quest-board.md`)の同時受注数が
  3件→4件に増える
- 「図鑑を全部埋める」→ `plan/monster-compendium.md` に記載の、
  かがやきの夢のかけら出現率上昇(図鑑側の報酬と実績側の表示を兼ねる)
- 「全NPCと一定以上の絆を築く」→ `design/village-life.md` の挿話が
  もう1段階分だけ追加で解放される(会話量が増えるだけで、数値効果はなし)

## データ構造

```ts
export interface SaveData {
  // ...既存フィールド
  achievements: Record<string, string>; // 実績id → 達成日時(ISO文字列)
  equippedTitle?: string;               // 現在身につけている称号id
}
```

達成判定は各機能の完了イベント(討伐・依頼達成・絆上昇・強化成功等)の
延長で `achievements` に追記するだけなので、実績専用の監視処理を
新設する必要はない(既存のイベント発生箇所に1行足す形で実装できる)。

## UI

拠点に「実績帳」を追加する(`design/village-life.md` の**肝いりのオトネ**
の所か、独立したメニュー項目かは実装時に判断)。未達成の実績は条件を
伏せずに一覧表示し、「あとどれだけで埋まるか」が常に見える形にする
(隠し実績は作らない方針。`design/balance-philosophy.md` の「反復感対策」
は明確な目標の提示で担うべきで、当てずっぽうの探索に頼らせない)。
