# テスト用の箱庭ダンジョン ― フロア状態を差し込み、ゲームUIフルセットで確認する

## 経緯

現状の自動テストは `tools/auto-tester.mjs`(実ダンジョンを乱数で
回すプレイテスト)に寄っており、単体テスト(vitest)が存在しない
(`npm test` はあるがテストファイルが1つも無い)。実ダンジョンは
`generateFloor` の乱数で作られるため、「この配置でこの挙動になるか」
という再現条件が組めず、あらゆる検証が困難になっている。

対策として、**フロアの状態を丸ごと外から差し込める箱庭**を用意する。
重要なのは、箱庭が動くのは**本物のゲームそのもの**だということ:
描画・HUD・タッチ操作・メニューまでフルセットで起動し、
**差し替わるのはダンジョンの状態だけ**。ロジックだけを切り出した
別物のミニゲームでテストするのではない(それでは UI・描画・入力の
バグが素通りする)。箱庭はテスト専用で、通常プレイからは一切
到達できない。

## 変更内容

### 1. 注入口 ― ゲーム起動時にフロア状態を差し込む

- ダイブ開始処理(`src/application/dungeonRun/game.ts` 系)に
  「`generateFloor` の代わりに、与えられた `FloorState` と
  プレイヤー初期状態でフロアを開始する」入口を1つ足す。
- この入口はテストモード(vite の `mode=test` 相当)でのみ
  コードに含め、**本番ビルドではビルド時定数のガードで
  デッドコード除去されて消える**。通常のUIからこの入口へ辿る
  導線は一切作らない。「ゲームからアクセスできない」の担保は
  この2点(本番から消える+導線なし)で行う。
- 注入内容: `FloorState` 全体、プレイヤー初期状態(レベル・
  満腹度・持ち物・仲間・装備)、使用する Rng、階数・地方などの
  メタ情報。つまり**乱数生成をバイパスする以外、ゲームは
  普段どおりに動く**。

### 2. 箱庭ビルダー(ASCIIマップでフロアを組む)

`tests/harness/floor.ts` に `buildTestFloor` を実装する。
`FloorState`(`src/core/types.ts`)を、乱数を使わず宣言的に
組み立てる:

```ts
const { floor, at } = buildTestFloor(`
  ##########
  #@...p...#
  #....#...#
  #..b.#..>#
  ##########
`, {
  legend: {
    p: { actor: "purun" },
    b: { barrel: "empty" },
  },
});
```

- 記号の既定: `#`=壁 `.`=床 `>`=階段 `@`=プレイヤー初期位置。
  それ以外の文字は `legend` で意味を与える(actor種族・残りHP、
  地面アイテム、罠、タル、金貨、障害物など、`FloorState` の
  各配列に対応)。
- 部屋(`rooms`)は矩形の床領域から自動検出する(視界処理の
  部屋依存ロジックを試すときだけ `rooms` を明示指定できる
  オプションを持つ)。
- `at("p")` のように、記号からタイル座標を引けるヘルパーを返す
  (アサーションで座標をハードコードしない)。
- ギミック(`gimmick`)・地方・階数もオプションで差し込める。
  省略時は「いつも通りの階」。

### 3. 決定的な乱数

- `tests/harness/rng.ts` に2種類のテスト用Rngを用意する:
  1. **シード固定Rng**: 本物と同じ実装をシード指定で。
  2. **列挙Rng**: `[0.0, 0.99, ...]` と値の列を直接渡し、
     「命中する/捕獲に失敗する」を意図どおりに踏ませる。
- ゲームロジックは既に `Rng` を引数で受け取る作りなので
  (`generateFloor(rng, opts)` 等)、注入口から差し替えるだけで
  済む。`Math.random` 直呼びが残っていたら、この実装のついでに
  `Rng` 経由へ直す。

### 4. テストの実行形態 ― 実ブラウザでゲームを丸ごと動かす

- テストランナーは **Playwright**(Chromium。実装環境に
  導入済みのものを使う)。`tests/e2e/*.test.ts` が
  1. vite をテストモードで起動し、
  2. ページ内の注入フック(テストモードでのみ window に生える)へ
     `buildTestFloor` の結果を渡してダイブを開始し、
  3. **本物のUIを本物の入力で操作する**(タッチ操作の
     エミュレーション・キー入力。内部APIを直接叩いて手順を
     飛ばさない)。
- アサーションは二層:
  - **状態**: 注入フックが読み取り専用のゲーム状態スナップショットを
    返す(HP・座標・持ち物・ログ)。挙動の検証はこれで行う。
  - **画面**: HUD・メニュー・メッセージのDOM/表示内容と、必要に
    応じたスクリーンショット。UIの検証はこれで行う。
- スマホ相当の検証のため、Playwright のデバイスプリセット
  (タッチ有効・モバイル画面サイズ)を既定にする。
  セーブ削除ボタン(#837)のようなタッチ限定UIもこの箱庭で
  テストできるようにする。
- `tests/` は `src/` から import されない(逆は自由)。CIに
  「`src/` 内に `tests/` への import が無いこと」の検査を足す。
- CI(`ci.yml`)にこの Playwright テストのジョブを追加する。

### 5. 最初に書くテスト(基盤の実証)

基盤PRに、少なくとも以下の3本を同梱して土台を実証する:

1. **移動と衝突**: タッチ操作で壁に向かって歩いてもターンを
   消費せず、床なら1マス進む(状態と画面の両方で確認)。
2. **戦闘の決定性**: 列挙Rngで乱数を固定し、隣接攻撃のダメージが
   期待値どおりで、ダメージ表示・ログがUIに出る。
3. **捕獲**: HPを削ったモンスターに空タルを当てて捕獲し、
   仲間に入ったことが状態とUI(メッセージ)の両方で確認できる。

以後、バグ報告(GitHub issue)には可能な限り「箱庭での再現
テスト」を添えて修正する運用にする(修正PRの受け入れ基準に
再現テストの同梱を推奨として書く)。

## 受け入れ基準

1. `tests/` の Playwright テストが、ASCIIマップで組んだフロアを
   注入して**本物のゲームUI上で**動き、上記3本が緑になる。
2. テストは `generateFloor` の乱数に一切依存しない。
3. 本番ビルド(`npm run build`)の成果物に注入口が含まれない
   (ビルド時定数ガードの除去をバンドル内容で確認)。通常プレイの
   どのUIからも箱庭に到達できない。
4. `src/` から `tests/` への import がCIで検出されたら失敗する。
5. ASCIIマップ・legend・注入フック・実行方法が
   `tests/harness/README.md` に実例つきで書かれている。

## 対象外

- モデル造形の見た目検証(`plan/models/archive/engine-preview-snapshots.md`
  が受け持つ。ただし箱庭のスクリーンショットはシーン全体の
  見た目検証にも流用できる)
- 村・拠点のシーンの注入基盤(まずダンジョンだけ。必要になったら
  同じ方式で広げる)
- 既存 `tools/auto-tester.mjs` の置き換え(乱数プレイテストは
  別役割としてそのまま残す)

## 未決事項

- 純ロジックの高速テスト(ブラウザなしの vitest 単体)を
  第2層として併設するか(まずUIフルセットの箱庭を正とし、
  実行時間が問題になったら検討)
- 盤面全体を検証するテストのアサーション形式(期待値もASCIIで
  書いて比較する案が有力。最初の3本には不要なので実装時に決める)
- 仲間AI・ボスAIの行動テストをどこまで箱庭で書くか

## 実装状況

1〜3・5は満たされた状態でアーカイブされていたが、受け入れ基準4
(`src/` から `tests/` への import をCIで検出する検査)が抜けていた。
`.github/workflows/ci.yml` の「型・テスト・ビルド」ジョブに
`src/` を `grep -rnE` で走査するステップを追加し、これで5項目とも
満たした。
