> **第一段階を実装済み。** `.github/workflows/deploy-pages.yml`(新規)。
> `main`へのpushのたびに`npm run build`し、`actions/upload-pages-artifact`
> → `actions/deploy-pages`でGitHub Pagesへ公開する(本文の擬似コードどおり、
> `checkout` → `npm ci` → `npm run build` → 公開)。`README.md`に試遊用の
> URLリンクを追加した。
>
> 実装にあたって次の判断をした。
>
> - **公開URLはGitHub Pagesの既定ドメイン
>   (`https://cyber-tribe.github.io/game/`)のままにした。** 未決事項の
>   カスタムドメインは見送り(本文でも「既定ドメインで十分か」は未決の
>   まま残されている選択)。
> - **リポジトリ側で GitHub Pages の Source を「GitHub Actions」に設定する
>   一度きりの手動操作が必要。** これはワークフローファイルの追加だけでは
>   自動化できないリポジトリ設定(Settings → Pages)で、実装セッションの
>   権限では変更できない。未設定のあいだはこのワークフローの`deploy`
>   ジョブだけが失敗するが、既存の`ci.yml`(型・テスト・ビルド、通しプレイ)
>   とは完全に別のワークフローなので、PRのマージ判定には一切影響しない。
> - **PRごとのプレビュー環境(段階2)は本文どおり見送った。**
> - `vite.config.ts`の`base: "./"`が既に相対パスのため、GitHub Pagesの
>   サブパス(`/game/`)配信にも変更なしで対応できた。

# テストプレイ環境の自動公開

現状、実際に触ってテストプレイするには `npm install` → `npm run dev`
というローカル環境構築が要る。自動化されているのは `npm run playtest`
(ヘッドレスブラウザでの決まった導線の自動確認、`tools/playtest.mjs`、
CI で毎回実行)だけで、**人が自由に触って試す**手段が整っていない。
ここでは `design/server-architecture.md` の3つ目の適用例として、
**mainへのマージのたびに最新ビルドをGitHub Pagesへ自動公開し、URLを
開くだけで誰でも試遊できる**ようにする。

## 位置づけ

- `npm run playtest` を置き換えるものではない。あちらは「決まった導線が
  壊れていないか」を毎回機械的に確かめるためのもので、これからも
  `ci.yml` に残す。
- 本文書が扱うのは、**人間が自由に(スクリプトが辿らない経路も含めて)
  触って試すための入口**。両方があって初めて「テストプレイが簡単に
  できる」と言える。

## 仕組み

```yaml
# .github/workflows/deploy-pages.yml (新規)
on:
  push:
    branches: [main]
jobs:
  deploy:
    steps:
      - checkout
      - npm ci
      - npm run build        # dist/ を作る(既存のビルド手順そのまま)
      - GitHub Pages へ dist/ を公開
```

- 静的サイトのホスティングだけなので、`design/server-architecture.md`
  の原則(秘密情報を埋め込まない・追加のシークレット不要)にそのまま
  沿う。`GITHUB_TOKEN` の既定の権限(`pages: write`)だけで完結する。
- README にビルド済みURLへのリンクを1本追加し、「まず触ってみたい人」
  がそこから入れるようにする。
- モデル(`public/models/*.glb`)は既にコミット済みのビルド成果物に
  含まれるため、追加の手当ては不要。

## セーブデータの扱い

このゲームはサーバーを持たず `localStorage` 完結(`src/save.ts`)なので、
公開ビルドで遊んだデータは**そのブラウザにだけ**残る。誰かのセーブが
他の人と混ざる・共有されるようなことは起きない。この点は変えない。

## 段階的な広げ方

1. **第一段階(本文書の対象)**: mainブランチの最新ビルドを常時1つ
   公開する。実装コストが最も低く、効果が大きい。
2. **将来の拡張(未決事項)**: PRごとのプレビュー環境(例:
   `https://.../pr-123/` のようなサブパスにデプロイし、PRへ自動で
   リンクをコメントする)。「Issueやコメントへ結果を書き戻す」パターンを
   流用できるが、実装コストが上がるため本文書の対象外とし、必要になれば
   別途仕様化する。

## 未決事項

- 公開URLの経路(GitHub Pagesの既定ドメインで十分か、カスタムドメインを
  用意するか)
- PRごとのプレビュー環境を作るタイミング(現時点では見送り、mainの
  常時公開で様子を見る)
- 公開ビルドと開発中の内容が食い違う瞬間(マージ直後の反映ラグ)を
  どう周知するか(READMEに「最新mainの内容です」と一言添える程度で
  十分と考える)
